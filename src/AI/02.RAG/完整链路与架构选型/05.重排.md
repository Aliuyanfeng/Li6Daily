## 五、重排——范式对比与级联设计

重排处理的是"候选集已定之后"的那一段。两个前提贯穿全章：**重排的收益以召回层的召回率为上限**，切分、索引、过滤造成的漏召重排修不了；**检索层指标与生成层指标不是同一件事**，用 `NDCG@k` 代替最终答案指标验收重排是常见错误（见 5.5.3）。

### 5.1 为什么需要重排

#### 5.1.1 双塔的表示瓶颈

双塔的分数形式是 `score(q, d) = sim(E_q(q), E_d(d))`：两侧独立编码，直到最后一步相似度计算才相遇，中间没有 token 级交互。三个后果是结构性的。

**表示瓶颈。** 文档侧向量必须在不知道 query 时预先算好，单个定长向量因此要承载"对任意可能问题"的相关性；而相关性是 query 与文档的联合属性，压缩必然带来信息损失。

**缺少逐词对齐能力。**"几个词同时出现且指向同一实体""否定""数值比较""条件限定"这类判据，内积结构都不擅长表达。典型症状是编号、版本号、错误码、函数名这类**词面精确匹配强、语义泛化弱**的查询，双塔经常输给 BM25——这也是实践中通常把混合检索排在重排之前的原因。

因此重排的问题可表述为：**在候选集已定的前提下，用无法预计算但交互更充分的分辨函数，重新估计 `P(relevant | q, d)`**。"无法预计算"不是缺陷而是精度来源——它允许编码时就看见 query。

#### 5.1.2 Cross-Encoder 的精度来源与根本代价

Cross-Encoder 把 query 与文档拼成一个序列（典型形式 `[CLS] q [SEP] d [SEP]`）送进同一个 Transformer，让**每一层都对 query token 与文档 token 做全交叉注意力**。精度优势来自 token 级交互，也来自训练目标可针对排序直接优化（pointwise 二分类、pairwise 排序、listwise 蒸馏等），不必受"文档表示与 query 无关"的约束。

代价是根本性的：**分数依赖 (q, d) 这一对输入，文档侧没有任何可复用的中间表示**。

```
重排总成本 ≈ 候选数 N × 单次前向成本(序列长度 L)
序列长度 L ≈ |q| + |d| + 特殊符号
单次前向的注意力成本 ∝ L²
```

双塔则文档表示离线算一次、在线只做向量比较（ANN 近似 O(log N)），两者在线复杂度差一个量级。由此得到两条结论：**能做的只有批处理提吞吐，改变不了"每个候选一次前向"；能压的只有 L（截断）和 N（级联）**——Cross-Encoder 因此只能出现在级联末端。另一个性质必须记住：**输出分数是判别性的、未校准的**，批内相对顺序可靠，但"0.7 分"在不同查询、模型、训练集之间没有可比含义，**绝对阈值不可移植、相对阈值才可用**。

#### 5.1.3 精度—成本谱系

| 位置 | 交互粒度 | 文档侧可否离线预计算 | 在线复杂度（单查询） | 精度（机制层面） |
| --- | --- | --- | --- | --- |
| 双塔召回 | 单向量内积，无显式交互 | 可 | 与语料规模相关（ANN 近似对数级） | 最低 |
| 迟交互 | token 级 MaxSim | 可（多向量） | 候选数 × token 数，可索引加速 | 中 |
| Cross-Encoder | 全交叉注意力 | **不可** | 候选数 × 一次完整前向 | 高 |
| LLM 重排 | 全交叉 + 生成式推理 | **不可** | 候选数（或列表级）× 一次解码 | 高（方差大） |

规律是：**交互越充分 → 越依赖 query 同时出现 → 越不可预计算 → 在线成本越高**；任何"既要 Cross-Encoder 精度又要双塔延迟"的方案，实质都是利用某种可缓存的中间量，而在精度上都会退让。

### 5.2 四种重排范式横向对比

#### 5.2.1 总览

| 维度 | Cross-Encoder | Late Interaction（ColBERT 类） | LLM-as-Reranker | 传统 LTR（GBDT 类） |
| --- | --- | --- | --- | --- |
| 判定方式 | 拼接后全交叉，输出分数 | token 级 MaxSim 聚合 | 生成式打分 / 比较 / 排序 | 特征驱动：多路特征 + 树打分 |
| 文档侧可否预计算 | 不能 | 能 | 不能 | 能（特征可离线算） |
| 单查询复杂度 | O(N) 次前向 | O(N) 次轻量矩阵运算 | O(N) 至 O(N²) 次 LLM 调用 | O(N) 次树推理 |
| 延迟 / 单次成本 | 中高 / 中（自有模型） | 低 / 低 | 高 / 高（按 token 计费或大模型推理） | 极低 / 极低 |
| 精度（机制层面） | 高 | 中高 | 高但不稳定 | 取决于特征与标注质量 |
| 典型候选规模 | 20–200 | 200–10000（可当第二级召回） | 5–50 | 100–1000 |
| 最适场景 | 末端精排、质量优先 | 大规模初筛 + 中等精度重排、存储预算受限 | 冷启动无标注、离线评估、小候选集 | 融合多路信号、延迟极敏感、有日志 |

"精度"列只给**机制层面的相对判断**：跨范式的精度高低依赖数据集、模型规模与训练数据，不同论文报告的优势幅度不可横向比较。

#### 5.2.2 Late Interaction：用 MaxSim 换可预计算

MaxSim：对 query 的**每一个 token** 向量，在文档所有 token 向量里取最大余弦相似度，再把各 query token 的最大值求和。

```
score(q, d) = Σ_{i ∈ query tokens} max_{j ∈ doc tokens} ( E_q[i] · E_d[j] )
```

这个式子解释三件事：**保留 token 级对齐**；**文档侧多向量可离线算好**（`E_d[j]` 不依赖 query，在线只做矩阵乘加取最大值）；**对剪枝友好**，因此能直接用向量索引做端到端检索，而不只是给第一级检索器当重排器。

ColBERT 原论文（Khattab & Zaharia，SIGIR 2020，arXiv:2004.12832）延迟但保留细粒度交互，使模型既有深度语言模型的表达力，又能离线预计算文档表示；据论文自报，结果与既有 BERT 类模型效果相当，同时执行速度快两个数量级、每查询 FLOPs 少四个数量级（**论文自报**）。代价是存储：多向量的空间占用比单向量高一个数量级；ColBERTv2（NAACL 2022，arXiv:2112.01488）用**残差压缩 + 去噪监督**把空间占用降低 6–10 倍，同时在训练域内外取得当时最好质量（**论文自报**）。压缩后的实际占用需实测。

#### 5.2.3 LLM-as-Reranker：三种打分粒度的成本结构完全不同

| 粒度 | 做法 | 调用次数 | 主要风险 | 适用 |
| --- | --- | --- | --- | --- |
| Pointwise | 逐条打分（分档、"是/否"、某标签词元概率） | O(N)（可合并为一次多条目 prompt，但会互相干扰） | 分数未校准、跨查询不可比；模型倾向给中间分 | 候选少、需要可解释分档 |
| Pairwise | 两两比较输出胜者，锦标赛聚合成全序 | O(N²) 或 O(N log N)（锦标赛） | 比较不满足传递性、顺序偏差 | 候选数很小、必须避免列表偏差 |
| Listwise | 一次交出整个候选列表，要求输出全排列或 Top-k | O(1) 次调用，但 prompt 长 | 位置偏差重、列表越长越不稳、格式约束难 | 小候选集（十几条内）、离线或低 QPS |

RankGPT（Sun 等，EMNLP 2023，arXiv:2304.09542）是 listwise 路线被引用最多的代表工作。据该论文自报：适当指令下的 LLM 在流行 IR 基准上可给出与有监督方法相当甚至更好的排序；作者构建了基于较新知识的测试集 NovelEval 以应对数据污染质疑；为落地效率用 permutation distillation 把排序能力蒸馏进小模型，其 440M 蒸馏模型在 BEIR 上超过 3B 的有监督模型（均为**论文自报**）。

**LLM 重排的核心工程问题不是精度上限，而是稳定性与成本模型。** *位置偏差*：候选顺序会显著影响模型选择，而该顺序来自第一级召回，抑制方法是多次打乱分别排序再用 RRF 等排名融合聚合，**代价是成本乘以打乱轮数**。*方差*：要求 `temperature=0`、固定提示模板与模型版本，并把模型版本写进缓存键（见 5.4.6）。*成本*：listwise 的 prompt 要装进 N 条候选全文，**容量规划必须按输入与输出 token 分别计价**。*失效模式*：LLM 对流畅但不相关的文本打分偏高，对需要精确匹配的判据反而不如小模型可靠；在专业领域（法务合同、医疗文档、内部代码库）上，通用模型的排序偏好可能与业务相关性不一致，**只能用领域标注数据微调或蒸馏来修**。

#### 5.2.4 传统 LTR 在 RAG 中的位置

LTR 按损失形式分 pointwise / pairwise / listwise 三类；GBDT 系的经典代表用"按指标变化加权"的梯度，直接以 NDCG 这类不可导指标的变化量调整样本权重。它在 RAG 里应被理解成**分数融合器，而不是语义匹配器**：输入是每 (q, d) 对的特征组（BM25 分、稠密相似度、迟交互分、Cross-Encoder 分、文档元数据），输出是最终排序分，合理位置是 `最终分 = LTR(召回分, 重排分, 元数据特征)`。优势是训练与推理极便宜（微秒级）、可解释，并能把时效、权威度、点击反馈等业务信号与重排分放在同一目标下优化；代价是需要标注或高质量日志，且对"特征里没有的新维度相关性"无能为力。因此在已做搜索排序的系统里，正确做法是把它当融合层，而不是另起一条排序链路。

#### 5.2.5 组合模式：什么时候用几级

主流级联是"召回 K1 → 轻量重排 K2 → 重量重排 K3 → 生成"三级或四级。四条要点：**每级只降一个数量级左右**；**级联的召回上限由第一级决定**，文档在第 i 级被丢弃后任何精度都找不回，因此必须按级监控 stage-wise recall；**收益递减点要实测**，依据是"再加一级重排，最终答案正确率是否显著提升"，而不是 NDCG 是否提升；**降级路径必须存在**（见 5.4.4）。

### 5.3 级联架构设计：K1 / K2 / K3 与延迟预算

#### 5.3.1 各级职责与优化目标不同

级联设计里最容易混淆的一点：**不同级的"好"不是同一个指标**。

| 级 | 产出 | 优化目标 | 指标 | 允许的错误类型 |
| --- | --- | --- | --- | --- |
| 召回（K1） | 大候选池 | 召回率优先 | Recall@K1（对答案文档） | 允许大量不相关文档混入 |
| 重排（K2 → K3） | 精排短列表 | 前若干位精度 | NDCG@K3 / Precision@K3 / Recall@K3 | 不能漏掉答案文档（漏了就进不了生成） |
| 生成 | 最终答案 | 忠实 + 正确 | 忠实度、答案正确率、引用正确率 | 允许说"资料不足" |

**约束一：K2 必须让"答案文档进入前 K2"的概率接近饱和。** 重排是提序不是剔除；若正确答案排第 40 名而 K2 设成 20，重排再准也没用——方法是统计答案文档在召回结果中的排名分布，把 K2 取在分布高分位之外（例如覆盖 98% 答案文档所需的最小截断位置）。**约束二：K3 由上下文预算与位置偏差决定**（见 6.1.1）；**"塞满窗口"通常降低质量并提高成本**，这是与直觉相反但可自测的结论。

#### 5.3.2 三档 K 值的确定方法

**K1** 由后续级的算力预算与答案文档的排名分布共同决定，经验上常在 50–200（经验区间，非实测结论）；判断式 `K1 = 覆盖 99% 答案文档所需的最小召回深度 × 安全系数`。**K2** 由重排器的成本模型反推：`K2 ≤ 延迟预算 ÷ 单条重排耗时`；有两个重排器时 K2 是轻量级输出、K3 是重量级输出（如 K2 = 50、K3 = 5–10）。**K3** 取三个约束的最小值：上下文 token 预算 ÷ 平均片段 token 数（硬预算）、位置偏差可接受的最大列表长度（越小越好）、评估集上测出的答案文档覆盖率饱和点。

**拐点的测法**：固定其他环节，把 K3 从 1 递增到预算上限，画"K3 — 答案正确率"与"K3 — 单次成本"两条曲线；正确率通常先升后平（甚至下降），成本线性上升，拐点（边际收益降至噪声以下）就是 K3。**拐点因语料、生成模型、问题类型而异，必须自测，不能照抄别人给的 K 值。**

#### 5.3.3 延迟预算怎么分配

下表是设计示例（**表中数值是示意值，不是实测值**，务必用自测数据替换）：

| 场景 | 端到端目标 | 召回 | 重排 | 生成 | 编排/网络 | 说明 |
| --- | --- | --- | --- | --- | --- | --- |
| 交互式对话（流式输出） | 首 token < 1 s | 30–80 ms | 80–250 ms | 首 token 其余 | 20–50 ms | 生成首 token 延迟是体验主项；重排必须在首 token 前完成 |
| 站内搜索/问答（非流式） | P95 < 2 s | 50–150 ms | 200–600 ms | 800–1400 ms | 50 ms | 生成占大头，重排有空间 |
| 离线批处理（评测/报表） | 分钟级 | 不限 | 不限 | 不限 | — | 可上 LLM 重排、多轮打乱聚合 |

两个要点：**生成层延迟由输出 token 数主导**，长上下文抬高的是**首 token 延迟**（prefill）与成本，输出长度决定总时长，两者不能互相替代；**重排延迟相对小，但它是每请求固定开销**，高 QPS 下转化为 GPU 容量成本，且每一级都必须设超时与降级（重排超时回落召回顺序，轻量重排超时直接进生成），降级占比要埋点告警。

#### 5.3.4 容量估算：从 QPS 反推 GPU 数量

```
QPS            每秒查询数
K2             每查询重排候选数
B              批大小（受显存限制）
t(B, L)        一个 batch 的前向耗时（与批大小、序列长度 L 相关，需实测）
U              目标利用率（留出尖峰余量与维护窗口，常用 0.5–0.7）

单卡每秒可处理的候选数  ≈ (B / t(B, L)) × 每卡并发流数
单卡每秒可服务的查询数  ≈ 单卡候选吞吐 ÷ K2
所需 GPU 数             ≈ QPS ÷ (单卡每秒查询数 × U)
```

三个偏离项。**延迟—吞吐权衡**：吞吐随 B 提升，等待时间也随 B 增加，达到"最大批等待时间"（如 10–20 ms）或"最大批大小"即发车，**提高吞吐与降低尾延迟直接冲突**，必须按 SLA 选点。**padding 浪费**：按条数组批会让短序列被 padding 到最长序列，正确做法是**按 token 预算组批**（`Σ L_i ≤ token_budget`）并按长度分桶。**估算必须自测**：`t(B, L)` 随模型、硬件、精度、实现差异可以有好几倍，外部数字不可直接采用，需自己扫描 (B, L) 网格。

### 5.4 工程实现要点

#### 5.4.1 批处理与显存

重排服务是"固定模型 + 变长输入 + 高并发小请求"负载，工程重点是让 GPU 不空转。

| 策略 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| 静态批 | 固定 B | 实现简单、延迟稳定 | 流量低谷时空转 |
| 动态批（时间窗） | 攒到"最大等待时间"或"最大批大小"即发车 | 吞吐显著提升 | 尾延迟上升，需按 SLA 定参数 |
| 按 token 预算组批 | 约束 `Σ L_i ≤ token_budget` | 减少 padding 浪费，显存可控 | 实现复杂，需长度分桶 |
| 长度分桶 | 按序列长度排序后切批 | 进一步减少 padding | 需缓冲排序，增加少量等待 |

```
显存 ≈ 权重              参数量 × 每参数字节（fp16 = 2 B，int8 = 1 B）
     + 激活与中间张量    ∝ B × L × 隐藏维度 × 层数 × 系数
     + 运行时工作区      ONNX / TensorRT 的 workspace、CUDA 图捕获等
     + 框架与上下文开销  通常几百 MiB 量级
```

（具体数值必须实测。）工程含义：**权重是常量开销，激活是随批变化的开销**，所以"显存不够就减批"往往有效，而"换量化权重"主要降低常量项、对小模型收益有限。

#### 5.4.2 序列长度与截断策略

自注意力成本随序列长度**平方**增长，显存占用随长度**线性**增长：长度翻倍时长序列段计算量约四倍、延迟明显上升，激活显存约两倍、更容易 OOM，从而被迫减小批大小并进一步降低吞吐。因此 **`max_length` 是重排服务最敏感的参数**，它同时影响延迟、显存、吞吐和精度。

| 截断策略 | 做法 | 优点 | 风险 |
| --- | --- | --- | --- |
| 尾部截断 | 只取文档前 L 个 token | 简单、成本最低 | 关键信息在后半段时直接丢失 |
| 头部截断 | 只取文档后 L 个 token | 对"结论在后"的文档有利 | 丢失背景与前文指代 |
| 首尾拼接 | 取前 L/2 + 后 L/2 | 兼顾两端 | 中间断层的语义跳跃，可能误导模型 |
| 滑窗取最大 | 把文档切若干窗，逐窗打分取最高分 | 不丢信息，召回最稳 | 成本乘以窗口数，延迟成倍上升 |
| 段落级预筛选 | 先取段内最相关段落再送精排 | 成本与精度平衡 | 依赖预筛选质量 |

选择依据是**答案位置在文档中的分布**：答案集中在前部（条款型文档、手册目录页）则尾部截断够用；长报告、手册类则滑窗取最大更稳但成本上升。常见折中是**离线用滑窗取最大、线上用尾部截断**，再比较两者的最终答案正确率差异——差异在噪声内就省下这笔成本。

#### 5.4.3 硬件选择与推理加速

| 条件 / 手段 | 建议或原理 | 收益 | 代价与前提 |
| --- | --- | --- | --- |
| QPS 低、K2 ≤ 20、延迟不敏感 | CPU 足够 | 省掉整条 GPU 运维链 | — |
| QPS 中高、K2 数十到数百 | GPU + 动态批 | 批处理在 GPU 上收益最大 | 需 batcher 与显存管理 |
| 无标注数据、要零样本重排 | 调 API 或自托管 LLM | 无需训练数据 | 见 5.2.3 的成本与稳定性讨论 |
| 知识蒸馏 | 用大模型/LLM 排序结果训练小模型 | 延迟与吞吐大幅改善 | 需蒸馏数据与一次训练；精度上限受小模型容量限制 |
| ONNX / TensorRT | 算子融合、内核与图级优化 | 同硬件下吞吐提升 | 导出与算子兼容性成本；调试信息变少 |
| 量化（int8/fp16） | 降低权重与激活位宽 | 显存下降、吞吐提升 | **精度损失需在评估集上验证**，不能默认无损 |
| FlashAttention 类实现 | 减少注意力的显存读写 | 长序列下显存与延迟改善 | 依赖硬件架构与算子支持 |

落地顺序：先"模型选型/蒸馏"，再"实现级优化"（ONNX、量化、内核），最后才考虑"用截断换延迟"；反过来做容易出现"极致优化了一个不该用的模型"。

#### 5.4.4 并发、吞吐与降级

服务端 batcher：应用侧提交单条请求，服务侧聚批执行；关键参数是最大批大小与最大等待时间，二者取先到者，等待时间直接加到 P99 上。降级顺序：

```
1. 重量重排（LLM / 大 Cross-Encoder）正常
2. 超时 → 回落到轻量重排（小 Cross-Encoder / 迟交互）
3. 轻量重排超时或不可用 → 使用召回顺序（RRF 融合结果）
4. 全部失败 → 直接把召回前 K 条送生成，并在响应中标记"未精排"
```

第 3、4 条是必须的：重排是纯优化环节，任何情况下都不应让整体请求失败；同时在指标上区分"使用降级结果"的请求占比，超过阈值就告警。并发模型上，重排服务**不该用多线程 Python 做前向**（GIL 与 CPU 侧前后处理限制），应交给 C++/CUDA 后端 + 单线程前端或多进程；Golang 服务端按标准 RPC 调用即可，但要设置合理的连接池与超时，避免 goroutine 堆积。

#### 5.4.5 截断策略：固定 Top-N 还是分数阈值

| 策略 | 保留规则 | 条数可预测性 | token 成本 | 跨查询自适应 | 主要风险 |
| --- | --- | --- | --- | --- | --- |
| 固定 Top-N | 总是保留前 N | 高 | 稳定 | 无 | 简单查询浪费预算，复杂查询可能不够 |
| 绝对分数阈值 | `score > τ` | 低 | 不定 | 中 | **分数未校准**，τ 在不同模型/查询间不可移植 |
| 相对分数阈值 | `score > α × max(score)` | 低 | 不定 | 好 | 若最高分是错的相关文档，会把正确文档一并截掉 |
| 混合（相对阈值 + 上下限） | 相对阈值 + N_min / N_max + token 预算 | 中 | 有界 | 好 | 需在评估集上调 α、N_min、N_max |
| 按生成预算反推 | 按 token 预算贪心填充 | 高 | 稳定 | 中 | 与相关性无直接关系，可能截断有用片段 |

**绝对阈值的提醒**：分数未经校准，跨模型、跨训练集、跨查询分布都不具备固定含义。确需绝对阈值时，应在验证集上做**分位数映射或概率校准**，且**每次换模型都要重新校准**。**相对阈值的失效模式**：`α × max(score)` 假设最高分可信，若第一级召回把一条"词面高度重叠但实际不相关"的文档排在第一，真正的答案会被全部截掉；缓解手段是设 `n_min` 兜底（如 3 条）、对多跳问题放宽阈值、结合召回分与重排分做双信号判定。

#### 5.4.6 重排结果的缓存策略

| 层次 | 缓存键 | 命中条件 | 收益 | 风险 |
| --- | --- | --- | --- | --- |
| 文档侧表示 | `doc_id + chunk_id + model_version` | 迟交互/稠密模型 | 高（离线即可完成） | 文档更新后必须失效 |
| (q, d) 重排分 | `hash(q) + doc_id + doc_version + model_version + prompt_version` | 相同 query 重复出现 | 高（FAQ、热门查询） | 键漏掉版本 → 换模型后读到旧分 |
| 查询→排序列表 | `hash(规范化 q) + 索引版本 + 模型版本` | 完全相同的查询 | 中高 | 索引增量更新后失效 |
| 查询→最终答案（语义缓存） | 相似度阈值匹配 | 相似查询 | 最高（省掉整条链路） | **串答案**：相似但实体不同的查询命中错误答案 |

**语义缓存必须谨慎**：相似度命中会让"如何重置管理员密码"与"如何重置普通用户密码"这类查询互相污染；若要用，阈值需足够高并经过验证、命中后做**实体一致性校验**（查询中的关键实体、订单号必须在缓存键的实体集合中）、条目记录原始查询以便审计回滚。失效设计三条规则：**键里带版本**（模型、提示模板、文档、索引版本）；**按 `doc_id` 前缀做事件驱动失效**（若缓存不支持按前缀删除，就不要缓存 (q, d) 分）；**模型上线即换命名空间**（键含 `model_version`，回滚时旧空间仍可用）。

#### 5.4.7 权限与多租户

**权限过滤必须在重排之前完成，且不得由重排分数推断。** 重排只改变顺序，不允许"因为分数低就顺带隐藏"或"因为分数高就顺带显示"；过滤是独立于打分的集合运算，应先过滤再重排。

**多租户缓存必须按租户隔离**（缓存键含 `tenant_id` 或按租户分命名空间），否则会泄漏存在性信息，甚至把 A 租户的排序结果返回给 B 租户。**重排也不得成为权限探测的放大渠道**：若"无权访问"时返回不同的分数或排序，外部输入方可用重排分数做存在性探测；无权访问的文档应在进入重排前被剔除，分数不对外暴露。

### 5.5 重排的收益与失效场景

本节的价值在于**抑制"加了重排就一定更好"的默认假设**：重排是有成本、有前提的优化手段，在相当多的场景里收益接近于零甚至为负。

#### 5.5.1 能改什么、不能改什么

**能改的**是候选池内文档的相对顺序，从而提升进入生成层的 K3 条片段中相关文档的比例；**不能改的**是召回率——第一级没召回的文档，重排无从知晓其存在。因此：

```
端到端正确率上限 ≤ 召回层 Recall@K1 × 重排层把答案提到前 K3 的能力 × 生成层利用证据的能力
```

**这个乘法结构是判断"该不该加重排"的第一性依据**：若 `Recall@K1` 只有 0.6（**此处仅为举例的假想数值，不是任何系统的实测结果**），把重排从"无"升级到"最强"最多把上限抬到 0.6 附近（重排只影响条件概率），远不如把召回率提到 0.85 划算。

#### 5.5.2 加重排几乎没有收益的典型场景

| 场景 | 为什么收益小 | 判断方式 |
| --- | --- | --- |
| 语料规模小、问题集中（几千个片段） | 稠密召回配合 ANN 的 top-5 往往已把答案放前面；重排解决的是大候选池里的混淆项 | 统计答案文档在召回结果中的平均排名，中位数已是 1–2 名则空间很小 |
| 单跳事实型问答，答案唯一且词面高度重叠 | 查询与文档共享大量实词（术语、产品名、错误码）时，词法或稠密检索已把正确文档排在第一 | 对比"仅词法检索"与"加语义重排"的答案正确率 |
| 生成层很强且 K3 足够大（20–30 条、成本不敏感） | 生成模型会自行聚焦相关部分，最终正确率可能对重排不敏感；**但成本对重排敏感** | 比较不同 K3 下的答案正确率与 token 成本 |
| 语料高度同质化（同模板条目、批量导入文本） | 候选间语义差异本就小，重排分差可能落在模型噪声内 | 同一查询多次重排结果间的 Kendall tau 稳定性 |
| 匹配依赖精确匹配信号（编号、订单号、函数名、版本号、流水线 ID） | 相关性由"字符串是否一致"决定；语义泛化反而可能把"讨论类似问题的另一个编号"提权 | 这类查询上，混合检索 + RRF 通常比重排更该优先做 |
| 通用重排模型与领域分布不匹配（法务合同、医疗文档、内部规章、内部代码库） | 通用模型的"相关性"与业务相关性不一致，可能把"语义相近但业务无关"的文档提前，**产生负收益** | 人工抽检重排前后 top-5 的业务相关性；修法是领域标注 + 微调/蒸馏 |
| 延迟预算极紧（端到端 P99 低于 200 ms 量级） | Cross-Encoder 的批等待与推理时间会吃掉预算 | 可行选项只有 tiny 模型、CPU 上的迟交互打分，或干脆不重排 |

#### 5.5.3 怎么判断重排到底有没有用

按顺序执行，任一步不通过就不要上线重排：**建离线评估集**（真实查询 + 人工标注的答案文档 ID）；**测召回上限**，算 `Recall@K1`，若显著低于目标先修召回层；**测排序质量**，对比"无重排"与"重排"的 `NDCG@K3` / `Recall@K3`；**测最终答案指标（关键一步）**——**只有当答案正确率与忠实度显著改善时重排才值得上线**，若只是 NDCG 改善而答案不变，重排只应作为成本优化手段评估；**在线 A/B**，同时监控 P95/P99 延迟与 GPU 成本。

#### 5.5.4 什么时候重排收益最大

以下条件同时成立时投入产出比最高：候选池大（十万级以上片段，K1 也大）；查询与文档存在明显词汇不匹配（用户用口语描述，文档用专业术语）；存在大量"语义相近但答案不同"的混淆项（同产品不同版本、同接口不同参数、相似工单不同处置）；生成预算紧（K3 小，必须优中选优）；有标注数据或可蒸馏的 LLM 排序输出。

一句话的工程判断：**重排不是"高级 RAG 的标配动作"，而是"当召回已经足够好、且候选池内存在显著混淆项时，用来把答案提到前面或把 K 值降下来的工具"。**
