## 二、全链路总览

### 2.1 两段式架构

RAG 的完整链路分成**两段**，它们的触发时机、性能要求、优化目标都不同。分清这一点是后续所有设计决策的前提。

```text
【离线索引链路】建库时执行一次；文档变更时对受影响部分重跑

  原始文档    →   解析清洗    →   切分    →   向量化    →   写入索引
  PDF / HTML      抽取纯文本      Chunk       Embedding     向量库
  Markdown        去噪、去重      父子块       批处理        倒排索引（稀疏路）
  数据库          统一格式        加元数据     归一化        元数据字段
                                                            （含权限、时间、来源）


【在线查询链路】每次提问执行；有明确的延迟预算

  用户提问  →  查询理解  →  召回  →  重排  →  生成  →  答案
              改写          多路并行   交叉编码器   Prompt     带引用
              分解          稀疏+稠密  精排        约束
              指代消解      融合(RRF)  Top-N       引用校验
```

**两段的关键差异：**

| 维度 | 离线索引链路 | 在线查询链路 |
| --- | --- | --- |
| 触发时机 | 建库时 / 文档更新时 | 每次用户提问 |
| 性能要求 | 吞吐优先，可容忍分钟级到小时级 | 延迟优先，通常要求秒级返回 |
| 失败代价 | 可重跑，影响面是数据新鲜度 | 用户直接感知，影响体验 |
| 优化目标 | 索引质量、更新成本 | 延迟、精度、成本三者平衡 |
| 常见瓶颈 | 解析质量、切分粒度、批量向量化耗时 | 向量检索、重排推理、生成 token 消耗 |

一句话概括：**离线链路的产出质量决定了在线链路的上限**。切分粒度不对、解析丢了三线表、元数据没带权限字段——这些问题在后面任何一个环节都补不回来。这是本文把切分单独讲一节的（3.2）原因。

### 2.2 各环节的产出与常见实现

| 环节 | 输入 | 产出 | 关键决策 | 常见实现 |
| --- | --- | --- | --- | --- |
| 解析清洗 | 原始文件 | 纯文本 + 结构信息 | 表格/代码怎么保留 | 各类文档解析库、专用解析服务 |
| 切分 | 纯文本 | Chunk 列表 | 粒度、是否重叠、父子关系 | 递归字符切分、语义切分、结构感知切分 |
| 向量化 | Chunk 文本 | 稠密向量 + 稀疏权重 | 模型选型、维度、归一化 | 各类 Embedding 模型 |
| 索引构建 | 向量 + 原文 + 元数据 | 可检索索引 | 索引算法与参数 | HNSW / IVF / DiskANN、倒排索引 |
| 查询理解 | 用户原始问题 | 规范化查询 | 是否需要改写、分解 | 查询改写、指代消解、HyDE |
| 召回 | 查询 | Top-K1 候选 | 单路还是多路、怎么融合 | BM25 + 向量检索 + RRF |
| 重排 | K1 个候选 | Top-K2 精选片段 | 用不用重排、用哪种 | Cross-Encoder / 迟交互 / LLM 打分 |
| 生成 | K3 个片段 + 问题 | 最终答案 | 上下文怎么组织、怎么约束 | Prompt 工程、引用校验 |

### 2.3 质量杠杆与成本杠杆

工程资源有限，要知道力气该往哪使。按**投入产出比**排序，实践中通常的优先级如下（**这是经验判断，不是实测结论**，你的数据分布不同可能顺序不同）：

**质量杠杆（按通常收益从高到低）**

1. **切分策略** —— 影响最大且最容易被忽视。切错了，后面所有环节都在为错误的输入做优化。
2. **混合检索** —— 向量检索与关键词检索的失效模式高度互补，多路召回通常比单路有明显提升。
3. **重排** —— 在召回候选已包含正确文档的前提下，重排能显著改善送入生成模型的片段质量。注意前提：**重排不可能修复召回阶段没捞回来的文档**。
4. **查询改写** —— 对口语化提问、多轮对话场景收益明显；对已规范的短查询收益有限。
5. **生成侧 Prompt 约束** —— 影响的是"有依据但答偏"和"无依据硬答"这两类问题，对检索本身无能为力。

**成本杠杆（按通常消耗从高到低）**

1. **生成模型的 token 消耗** —— 通常是整条链路最大的持续性成本，且与 K3 和片段长度成正比。
2. **重排模型的推理算力** —— 若自托管，需要 GPU 且成本与 K1、序列长度成正比。
3. **向量库的内存占用** —— 向量本体 + ANN 图结构常驻内存，规模上去后是硬成本。
4. **向量化的批量计算** —— 一次性或增量成本，通常可接受。

一个务实的结论：**先在低成本的环节上把质量做够**（切分、混合检索），再考虑引入重排这类需要额外算力的组件。顺序反了，容易花了大成本却收效甚微。

### 2.4 建议的推进顺序

不要一上来就把所有组件都堆上。分阶段推进，每一阶段都能独立上线并产生价值：

| 阶段 | 做什么 | 验证目标 |
| --- | --- | --- |
| 第一阶段 | 解析 + 切分 + 单路向量检索 + 生成，配最简 Prompt | 链路能跑通，答案基本可用 |
| 第二阶段 | 加混合检索（补一路关键词检索并融合） | 专有名词、编号类查询的召回明显改善 |
| 第三阶段 | 加重排，确定 K1/K2/K3 | 送入生成模型的片段质量提升，答案准确率提升 |
| 第四阶段 | 建离线评估集，做参数寻优；加引用校验与拒答 | 效果可量化、可回归，减少胡编 |
| 第五阶段 | 按需引入查询改写、上下文压缩、权限过滤等增强 | 针对性解决已定位的问题 |

每一阶段都应先建立**可测量的评估手段**（见第九章），否则无法判断改动是变好还是变坏——很多时候，凭直觉的"优化"实际是负收益。
