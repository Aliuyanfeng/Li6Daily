## 四、召回——检索范式、融合与索引调优

### 4.1 检索范式对比

| 范式 | 代表实现 | 表示形式 | 匹配机制 | 语义泛化 | 精确匹配 | 索引结构 | 训练依赖 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 稀疏（词项） | BM25 | 高维稀疏词频向量 | 词项重叠 + 统计加权 | 弱（同义、改述失效） | 强 | 倒排索引 | 无 |
| 学习式稀疏 | SPLADE 等 | 稀疏但词项被语义扩展 | 词项重叠，权重由神经网络生成 | 中 | 较强 | 倒排索引 | 需要 |
| 稠密（双塔） | SBERT / DPR / 各类 embedding API | 低维稠密向量 | 向量相似度 | 强 | 弱（编号、标识符易丢） | HNSW / IVF / DiskANN | 需要 |
| 迟交互 | ColBERT | 多向量（token 级） | 保留细粒度 token 交互后聚合 | 强 | 较强 | 多向量索引 | 需要 |
| 混合 | BM25 + 稠密 + 融合 | 两路以上 | 排名融合或分数融合 | 强 | 强 | 两套索引 | 视组件而定 |

这张表的读法是"失效模式"而不是"性能排名"。稀疏路的失效模式是"字面不同"，稠密路是"字面相同但语义被压缩"，迟交互处在两者之间，混合的作用是让两套失效集合尽量不重合。

#### 4.1.1 学习式稀疏：SPLADE

SPLADE 解决的问题是：**既要倒排索引的精确匹配与效率，又要神经网络的语义扩展能力**。其核心思想（来源：SPLADE 论文，SIGIR 2021 short）是用带掩码语言模型（MLM）头在**整个词表维度**上为每个文档/查询生成权重，再通过显式的稀疏性正则（对权重做 L1 类约束）与**对数饱和**（压制高频词项的过大权重）使结果高度稀疏，从而直接落到倒排索引上，同时保留词项维度上的"语义扩展"——文档会在词表上激活语义相关的**其他词项**，检索时仍按词项重叠打分。论文摘要的关键表述是"基于显式稀疏正则与词项权重对数饱和"，并"在效果与效率之间通过控制稀疏正则的贡献来做权衡"（来源同上）。具体公式此处不展开，实现时以论文原文与开源实现为准。

| 维度 | SPLADE 相对 BM25 | SPLADE 相对稠密 |
| --- | --- | --- |
| 语义泛化 | 明显更好（词项扩展） | 略弱于最强稠密模型（幅度未核实） |
| 精确匹配 | 保持（仍是词项重叠） | 明显更好 |
| 索引 | 仍是倒排，但文档表示更长（非零维度更多） | 倒排 vs 向量索引，取决于硬件 |
| 成本 | 建索引需 GPU 前向；查询需一次模型前向 | 查询延迟相近，SPLADE 对 CPU 倒排更友好 |
| 运维复杂度 | 中（模型 + 倒排） | 低（向量库即可） |

工程判断：SPLADE 的收益主要在"必须在倒排生态里做语义检索"的场景（已有 Elasticsearch/Lucene 集群、不想引入向量库）。如果已经规划了向量索引，混合检索（BM25 + 稠密）通常是更省事的路径。

### 4.2 BM25：k1 与 b

#### 4.2.1 从 TF-IDF 到 BM25 的三处改进

TF-IDF 的朴素形式是 `tf × idf`，有三项经验缺陷：长文档天然词频高因而被系统性抬高；同一词项出现 100 次和 10 次的相关度差异被线性放大；idf 缺少上界约束。BM25 在此基础上引入三件事：**词频饱和**，单个词项的贡献随出现次数递增但有上界，参数 `k1` 控制饱和速度；**文档长度归一化**，参数 `b` 控制长度惩罚强度；**保留 idf 的统计形式**，稀有词项贡献大。

```text
score(q, d) = Σ_{t ∈ q}  idf(t) · ( f(t,d) · (k1 + 1) ) / ( f(t,d) + k1 · (1 - b + b · |d| / avgdl) )
```

其中 `f(t,d)` 是词项频次，`|d|` 是文档长度，`avgdl` 是集合平均文档长度。idf 存在多种平滑形式（带 `+0.5` 的一类变体较常见），具体实现以所用检索引擎源码为准。

#### 4.2.2 参数含义与调优方向

Elasticsearch 官方文档明确：BM25 为 text/keyword 字段的默认相似度，`k1` 默认 `1.2`，`b` 默认 `0.75`；同一文档还给出 LM Dirichlet 的 `mu` 默认 `2000`、LM Jelinek Mercer 的 `lambda` 默认 `0.1`（来源：Elasticsearch 文档，*Similarity settings*）。这些默认值的意义在于：**它们不是"正确值"，而是通用语料上的稳健起点**。

| 参数 | 作用域 | 调大 | 调小 | 调优信号 |
| --- | --- | --- | --- | --- |
| `k1` | 词频饱和速度 | 高频词的边际收益更持久，长文内重复命中更强的文档被抬高 | 更快饱和，接近二值"是否包含" | 若"词项出现次数"确有判别力（例如日志正文里同一次故障的多次出现），可上调；若噪声重复多，下调 |
| `b` | 长度归一化强度 | 更严厉惩罚长文档 | `b=0` 关闭长度归一化 | 语料内文档长度本身不携带相关性时下调；短查询匹配长文档噪声大时上调 |
| `discount_overlaps` | 重叠 token 的 norm 计算 | — | — | 同义词扩展场景需注意重叠 token 对文档长度统计的影响（ES 文档已说明该选项） |

工程上更值得注意的不是微调 `k1`/`b`，而是**分词与字段构造**：检索 ID、订单号、商品 SKU、产品型号、API 名称、函数名这类标识符必须不被分词器切碎。这一点的收益通常大于参数调优。

#### 4.2.3 为什么 BM25 对专有名词、编号、代码标识符有效

BM25 的评分完全建立在"查询词项是否出现在文档中"之上，不做语义投影，因此不存在"语义相近但字面不同"与"字面相同但被编码器压缩掉"这两类损失。Anthropic 的技术文章给了一个具体例子：用户查询 `Error code TS-999` 时，embedding 模型可能召回"泛泛讲错误码"的内容，却漏掉字面匹配的 `TS-999` 文档，而 BM25 会精确命中该字符串（来源：Anthropic，*Introducing Contextual Retrieval*）。

这类"字面即语义"的标识符在工程语料里非常密集：工单号、订单号、商品 SKU、产品型号与版本号、API 名称、函数名与类名、Go 的包路径、Python 的 dotted path、`0x` 前缀的硬编码常量、配置键名。对这类查询，纯稠密检索的召回率通常显著下降，原因是子词分词把强判别性 token 切成无意义片段并被平均到同一向量空间。由此得到一条优先级建议：**先把分词与字段构造做对，再考虑调参**——为标识符类字段单独建 `keyword` 子字段；把编号类字段声明为 exact match 并进入过滤条件；对代码路径类内容保留原始分隔符不做归一化。

#### 4.2.4 稀疏检索的优缺点

| 维度 | 表现 | 原因 |
| --- | --- | --- |
| 精确匹配 | 强 | 不倒逼语义空间，字面命中即得分 |
| 可解释性 | 强 | 可以逐词项解释得分构成 |
| 冷启动 | 无训练成本 | 无需标注、无需 GPU |
| 更新成本 | 低 | 增量建倒排索引，实时性可达秒级 |
| 同义/改述 | 弱 | "如何配置缓存过期"匹配不到"缓存 TTL 设置"这种表述 |
| 跨语言 | 弱（除词典/翻译扩展） | 词项不同即不匹配 |
| 词表外/拼写错误 | 弱 | 无模糊语义韧性 |

### 4.3 稠密双塔

#### 4.3.1 原理与"为什么必须双塔"

双塔 = 两个独立编码器（实践中常共享权重或为同一模型的两个使用方式），分别把查询和文档映射到同一向量空间，相关性用向量相似度近似：`sim(q, d) ≈ ⟨ E_q(q), E_d(d) ⟩`。

**双塔之所以是双塔，根本原因是内积的可分解性**：`⟨E_q(q), E_d(d)⟩` 中 `E_d(d)` 与查询无关，因此可以离线对全语料预计算并建立向量索引。交叉编码器把 `(q, d)` 拼接后一起前向，表达力更强，但每个 `(q, d)` 对都要跑一次完整前向，无法预计算，只能用于对少量候选做重排。

这个差异的量级有可定位的数字支撑：SBERT 论文指出，用 BERT 在 10,000 个句子中找最相似句子对约需 5,000 万次推理（约 65 小时），而 SBERT 把这个过程降到约 5 秒（来源：Sentence-BERT 论文）。DPR 论文进一步验证了"仅用稠密表示即可实现检索"，其双编码器框架在多个开放域问答数据集上相对 Lucene-BM25 的 top-20 段落召回准确率提升约 9%–19%（绝对值）（来源：DPR 论文，EMNLP 2020）。

代价是表达力的损失：`E_d(d)` 是固定维度向量，无法在编码时感知查询，因此**细粒度的条件匹配、多跳约束、否定语义容易被压缩掉**。这既是稠密检索漏召回的根因，也是混合检索有效的根因。

| 架构 | 查询时每篇文档成本 | 可否预计算文档表示 | 表达力 | 典型用途 |
| --- | --- | --- | --- | --- |
| 双塔 bi-encoder | O(1) 次向量比较（可用 ANN 亚线性） | 可以 | 中 | 召回第一层 |
| 交叉编码器 cross-encoder | O(1) 次完整前向 | 不可以 | 高 | 重排（top-50 ~ top-200） |
| 迟交互 late interaction（ColBERT） | O(token 对数) 次比较 | 可以（文档 token 向量离线） | 中高 | 召回 + 重排折中 |

ColBERT 的设计动机与收益有来源支撑：它对查询与文档分别编码，保留 token 级交互且文档表示可离线预计算，论文摘要称其在效果上与 BERT 类模型相当的同时，执行速度约快两个数量级、每查询 FLOPs 约少四个数量级（来源：ColBERT 论文，SIGIR 2020）。迟交互索引的存储开销远高于单向量（每文档存多个向量），这是它在 RAG 工程中不如"单向量稠密 + 交叉编码器重排"流行的主要原因。

#### 4.3.2 选型的依据

不要凭记忆里的榜单选模型，用两个公开评测体系做初筛，再用自己的标注集做终选。

**BEIR**：跨 18 个数据集、覆盖多种检索任务与域的零样本评测，评测了 10 个系统（词法、稀疏、稠密、迟交互、重排）。核心结论：**BM25 是稳健的基线**；迟交互与重排在零样本下平均最好但计算代价高；稠密与稀疏模型更便宜，但在零样本跨域场景下经常不如前者（来源：BEIR 论文，NeurIPS 2021 D&B）。这条结论直接支持"先上 BM25 基线，再谈稠密"的推进顺序。

**MTEB**：8 类 embedding 任务、58 个数据集、112 种语言、33 个模型的评测，结论是**没有单一方法在所有任务上占优**（来源：MTEB 论文）。工程含义很直接：不要用一个 leaderboard 平均分选模型，要按自己的任务类型（检索/聚类/分类/重排）和语言分布选。

双塔检索的代表模型族（仅作谱系陈列，不给出版本号与参数量）：

| 族 | 训练/设计特征 | 工程定位 |
| --- | --- | --- |
| Sentence-Transformers / SBERT 系 | 孪生与三元组结构，目标函数为余弦相似度，开源变体覆盖多语言与若干领域 | 通用语义检索的基础路线；有公开实现与大量微调变体 |
| DPR 系 | 双编码器 + 批内负样本 + 少量困难负样本，面向开放域问答的段落检索 | 需要"以问答对微调"的检索任务 |
| 通用检索 embedding 系（各开源权重家族） | 对比学习 / 指令式训练，模型卡自带推荐指令前缀与归一化约定 | 开箱即用的第一层召回；**必须遵守其模型卡的 query/passage 前缀与是否归一化的约定** |
| 迟交互系（ColBERT 类） | 文档 token 级多向量、MaxSim 聚合 | 召回质量接近交叉编码器且文档表示可离线，但索引体积大 |
| 商用 embedding API | 托管模型，通常与自家重排模型配套 | 省运维；需注意数据出境、限流与版本变更对索引的影响 |

Anthropic 在其 Contextual Retrieval 实验中提到，在其测试的嵌入模型里 Gemini 与 Voyage 的 embedding 效果较好（来源：Anthropic，*Introducing Contextual Retrieval*）——这是**其特定实验配置下的结论**，不构成通用推荐。

#### 4.3.3 训练信号（如果要自己微调）

最关键的一点是负采样策略。DPR 的贡献之一就是用**批内负样本**（同一 batch 中其他问题的正段落）加少量困难负样本，在少量问答对上学到可用的检索表示（来源：DPR 论文）。工程上如果语料领域特殊（内部工单、专有术语密集的技术文档、代码库），微调双塔的收益通常大于换一个更大的通用模型。

### 4.4 混合检索与融合策略

#### 4.4.1 为什么混合通常优于单路

其一，**误差互补**。稀疏路的失效模式是"字面不同"（同义、改述、跨语言），稠密路的失效模式是"字面相同但语义被压缩"（编号、标识符、罕见专名）。两路失效集合高度不重合，取并集能覆盖单路漏掉的样本。这是机制层面的判断，不是实测结论。

其二，有公开基准支撑。BEIR 的评测结论中，重排与迟交互方法平均最好而 BM25 是稳健基线，稠密与稀疏单独使用在零样本下经常不及（来源：BEIR 论文）；Anthropic 的实验中"Embeddings + BM25 优于仅 Embeddings"，且该收益与其上下文增强、重排**可叠加**（"All these benefits stack"）（来源：Anthropic，*Introducing Contextual Retrieval*）。

其三，有可量化的真实案例。Anthropic 报告在其多领域实验（代码库、小说、arXiv 论文、科学论文）中，组合 Contextual Embeddings 与 Contextual BM25 把 top-20 召回失败率从 5.7% 降到 2.9%（降低 49%）；再加一层重排降到 1.9%（降低 67%）（来源同上）。

需要提醒：引用这些来源的结论，不等于在自己的语料上验证过。BEIR、MTEB 这类结论是跨数据集平均值，落到具体领域（日志、专有术语密集的文档、代码库）时排序可能完全不同。

#### 4.4.2 RRF（Reciprocal Rank Fusion）

RRF 只用**排名**，不用分数，因此天然规避了"不同检索器的分数不可比"问题。Elasticsearch 文档给出的计算形式（来源：Elasticsearch 文档，*Reciprocal rank fusion*）：

```text
score(d) = Σ_{q ∈ Q} 1 / ( k + rank(result(q), d) )
```

其中 `rank` 从 1 开始，`k` 是排名常数。RRF 的官方描述强调它"无需调参（requires no tuning）"，且"不同的相关性指示器之间不需要相互有关系"（来源同上）。

| 参数 | 含义 | Elasticsearch 默认 | 调优方向 |
| --- | --- | --- | --- |
| `rank_constant`（公式中的 k） | 控制高排名与低排名文档的影响力差异。官方说明：值越高，低排名文档影响力越大 | `60` | 数值越大越"平滑民主"，越小越"头部集中" |
| `rank_window_size` | 每个子检索器返回的候选集大小；决定最终可排序的并集范围 | 默认等于请求的 `size` | 收窄会使部分系统的高排名文档在并集中缺失，从而改变最终排序（ES 文档给出了该效应的具体数值例子） |

关于 `k=60` 的溯源：Elasticsearch 明确把默认值设为 60，并指向 Cormack 等人的 SIGIR 2009 论文（来源同上）。**原始论文中使用的 k 值未取得可定位证据**，工程上把 k 当作可调常数处理即可。

RRF 的工程性质：无需分数归一化、对不同分数量纲鲁棒、实现简单、可扩展到任意路数（BM25 + 稠密 + 学习式稀疏 + 规则打分）。缺点是**丢弃了分数幅值信息**——如果某一路的分数差距极其显著（同一文档被两路都以压倒性优势排第一），RRF 也无法体现这种"置信度"。

#### 4.4.3 加权分数融合（Convex Combination）

`score(d) = α · s_sparse(d) + (1 - α) · s_dense(d)`。这个策略看起来更"精确"，但引入一个 RRF 不存在的问题：**两路分数不可比**。BM25 的分数无上界（取决于集合统计量，量级可到几十），余弦相似度在 `[-1, 1]`（实际检索中通常落在 `[0.3, 0.9]` 的窄区间）。直接线性组合会让 BM25 完全支配结果。

| 归一化方法 | 做法 | 问题 |
| --- | --- | --- |
| Min-Max（按本次查询的候选集） | `(s - min) / (max - min)` | 结果依赖候选集构成：本次查询的"最低分"是相对的，导致同一文档在不同查询下归一化分数漂移；单候选时除零 |
| Z-score | 减均值除标准差 | 假设分数近似正态，BM25 的长尾分布不满足；候选集小时统计量不稳 |
| 理论界截断 | 用相似度的理论上下界（如余弦 `[-1,1]`） | BM25 没有通用上界，只能截断/饱和，会损失区分度 |
| 分数→排名再映射 | 对每路分数做序数变换后用 RRF 类公式 | 相当于回到 RRF，不如直接用 RRF 简单 |

结论性建议：需要与业务权重挂钩（例如"宁可多召回字面命中"）时用加权融合，但必须显式实现归一化并把 α 纳入离线评估的搜索空间；否则优先 RRF，它的"无需调参"性质能显著减少回归风险。

#### 4.4.4 三种融合方式对比

| 维度 | RRF | 加权分数融合 | 加权 RRF（每路一个权重） |
| --- | --- | --- | --- |
| 输入 | 排名 | 归一化分数 | 排名 |
| 需要分数归一化 | 不需要 | 需要 | 不需要 |
| 承载"置信度/幅值" | 否 | 是 | 否（仅路级权重，非文档级） |
| 可调参数 | k（+ 窗口） | α（+ 归一化方式） | 各路权重 + k |
| 过拟合风险 | 低 | 中到高 | 低到中 |
| 实现成本 | 低 | 中 | 低 |
| 适用 | 默认首选；多路异构检索器 | 两路、量纲可控、有充足标注评估 | 某一路已知更可信（如字面命中优先） |

### 4.5 查询侧优化

前提认知：**用户原话往往不是好的检索查询**。它短、含指代、含隐式约束、含多个子问题。查询侧优化的性价比通常高于更换向量模型。

#### 4.5.1 四类手段对比

| 手段 | 做法 | 解决的问题 | 代价 | 风险 |
| --- | --- | --- | --- | --- |
| 查询改写（rewrite） | 用 LLM 把口语/含指代的查询改写为规范的检索查询 | 指代消解、口语化、字段补齐 | 1 次 LLM 调用（延迟 + 成本） | 引入幻觉，改写后偏离原意；改写失败时反而降低召回 |
| 查询扩展（expansion） | 增补同义词、上位词、领域术语 | 词汇失配 | 可纯词典实现（零 LLM 成本）或 LLM 实现 | 扩展过宽导致主题漂移、精度下降 |
| 多查询（Multi-Query） | 生成 N 个改写/子查询，各自检索，再融合（也常做 RRF） | 单查询表达不全面 | N 倍检索开销 + 1 次 LLM | 需要去重与融合；N 过大时尾部长尾噪声进入候选 |
| 查询分解（decomposition） | 把复合问题拆成子问题，分别检索后合成 | 多跳、多约束问题 | 多次检索 + 合成逻辑复杂 | 子问题分解错误会系统性漏召回 |

选择依据：如果失败模式是"用户问的是同一个意思但用词不同"，用扩展或多查询；如果是"一次问了两件事"，用分解；如果是"追问里全是代词"，用会话改写。

#### 4.5.2 HyDE

原理（来源：HyDE 论文）：让指令微调过的语言模型基于查询**零样本生成一篇假想文档**，再用一个无监督对比学习过的编码器（论文中的例子是 Contriever）把它编码成向量，用该向量在语料空间里检索邻近的真实文档。论文摘要明确指出该假想文档"捕捉了相关性模式但不真实、可能包含错误细节"，而第二步的关键在于**编码器的稠密瓶颈会过滤掉错误细节**，把生成内容"落地"到真实语料上（来源同上）。论文报告其在多种任务与语言上显著优于无监督稠密检索器 Contriever，并接近微调过的检索器（来源同上）。工程含义在于：HyDE 的价值集中在**没有相关性标注**的场景——它把"查询→文档"的不对称匹配，转成"文档→文档"的对称匹配，而后者正是稠密编码器被训练好的方向。

| 维度 | HyDE 的实际情况 |
| --- | --- |
| 每次查询的额外成本 | 1 次生成（几十到几百 token 输出）+ 1 次编码 |
| 延迟影响 | 取决于生成模型；流式无用，必须等全文生成完才能编码 |
| 失败模式 | 生成内容完全跑偏（领域外问题、极短查询）→ 检索到"长得像假想文档"的无关内容；生成内容过于通用 → 检索退化为泛化匹配 |
| 与混合检索的关系 | HyDE 只改善稠密路；字面路（BM25）不能用假想文档替代查询，否则丢失精确匹配能力 |
| 何时不该用 | 查询本身已含强字面约束（编号、标识符、错误码）时，HyDE 反而可能把字面信号抹掉 |
| 与查询改写的关系 | 二者可叠加，但都在生成侧引入幻觉，需要监控 |

Anthropic 在其文章中把 HyDE 列为"过去已提出的其他利用上下文改进检索的方法"之一，并明确说明其做法与这些方法不同；同文提到其评估过的"给块加通用文档摘要"与"摘要式索引"两种思路收益有限或表现偏低（来源：Anthropic，*Introducing Contextual Retrieval*）。这说明"用摘要/假想文本增强"并非无代价的免费午餐。

#### 4.5.3 会话场景的指代消解

面向多轮对话的 RAG，最常见的召回失败不是语义问题，而是**查询本身不自足**。典型："它的参数是什么"——检索器不知道"它"是谁。

| 做法 | 机制 | 成本 | 适用 |
| --- | --- | --- | --- |
| 基于对话历史的改写 | 把最近 N 轮对话与当前问题一起交给 LLM，输出自足的独立查询（standalone query） | 1 次调用 | 主流做法，覆盖大多数场景 |
| 确定性规则补全 | 当上一轮的唯一实体/话题可由元数据定位时（例如上一轮回答引用了 `chunker` 组件文档），直接用该实体拼查询 | 零 LLM 调用 | 高确定性、延迟敏感场景 |
| 双查询并行再融合 | 同时使用改写查询与原始查询检索 | 额外一路检索 | 改写失败时原始查询兜底 |

必须做的三件事：**保留原始查询**，用于日志、评估与回退，否则线上问题无法复现；**限定历史窗口**，过长的历史会把当前话题稀释，改写模型会偏向更早的话题；**把改写纳入离线评估**，改写质量的退化会直接表现为召回率下降，但根因在改写，不评估就查不到。

#### 4.5.4 编排顺序

前置越靠前，代价越低但作用越基础。

```text
原始查询
  → (会话场景) 指代消解 / 改写        成本：1 次 LLM
  → (可选) 查询分解为子问题            成本：1 次 LLM + 多路检索
  → (可选) 扩展 / 多查询               成本：词典或 1 次 LLM + 多路检索
  → 并行：BM25 路 + 稠密路（+ 可选 HyDE 只作用于稠密路）
  → 融合（RRF / 加权）
  → (可选) 元数据过滤（见 4.7，位置决定召回率上限）
  → (可选) 交叉编码器重排
  → top-k 送入生成
```

### 4.6 向量索引结构

这一节决定的是**延迟、内存和召回率的三角关系**。

#### 4.6.1 HNSW

原理（来源：HNSW 论文）：HNSW 是一个完全基于图的近似最近邻结构，构建一个**多层邻近图**，每层包含前一层元素的嵌套子集；元素能出现的最高层按**指数衰减的随机分布**选取，从而让"边按其特征距离尺度分层"；搜索从上层开始逐层下降，这种尺度分离使复杂度呈现**对数级增长**；再配合**邻居选择的启发式**，在高召回区间和高度聚类的数据上显著提升性能。论文还说明该算法与跳表结构的相似性，因此便于做平衡的分布式实现（来源同上）。翻译成工程直觉：上层稀疏、跨距大，用来快速逼近目标区域；下层密集、跨距小，用来精确定位。下层图包含"捷径边"（存在比几何邻居更远的连接），这正是小世界网络能跳出局部簇的原因。

| 参数 | 阶段 | 含义 | 调大 | 调小 | 调优信号 |
| --- | --- | --- | --- | --- | --- |
| `M`（每层最大连接数） | 构建 | 每个元素的邻居边数量 | 图更稠密，高召回下更快达到目标、对聚类数据更稳；内存与构建时间上升 | 内存省、构建快；高维或高聚类数据下召回下降 | 内存受限且召回不达标时优先考虑；先在 16–48 区间试（经验值） |
| `efConstruction` | 构建 | 构建时动态候选列表大小（搜索宽度） | 图质量更好，召回上限更高；构建时间线性上升 | 构建快；图质量差，后续 `efSearch` 加多大也补不回来 | 构建是一次性成本，通常宁可调大 |
| `efSearch`（查询时的 `ef`） | 检索 | 查询时的候选列表大小 | 召回上升、延迟上升，呈"先快后平"的边际递减 | 延迟下降、召回下降 | 线上唯一可动态调整的旋钮；按 P95 延迟预算反推可取的最大值 |
| 距离度量 | 构建 + 检索 | 余弦 / 内积 / L2 | — | — | 必须与 embedding 的训练目标一致，见 4.6.5 |

关键调优点是：`efConstruction` 决定**质量上限**，`efSearch` 决定**实际工作点**。用低质量图 + 大 `efSearch` 去补，是常见的性能陷阱——延迟上去了，召回却达不到高质量图在中等 `efSearch` 下的水平。HNSW 的结构性限制有三条：删除支持弱（软删除 + 定期重建是常见实践）、内存必须能容纳图与向量（可用压缩量化缓解）、以及**带元数据过滤时会破坏连通性**（见 4.7）。具体实现的默认参数值请以所用库的文档为准。

#### 4.6.2 IVF-Flat 与 IVF-PQ

**IVF-Flat**：先用 k-means 把向量空间聚类成 `nlist` 个单元（倒排桶）；查询时用查询向量找到最近的 `nprobe` 个单元，只在这几个单元内做**精确**距离计算。召回率随 `nprobe` 单调上升，`nprobe = nlist` 时退化为暴力检索。它保留全精度向量，因此**不引入量化误差**，代价是内存仍是全精度。

**IVF-PQ（乘积量化）**：把 `d` 维向量切成 `m` 个子段，每个子段独立做 k-means 量化（常用 256 个中心，正好一个字节），于是每个向量被编码为 `m` 字节。压缩比（估算，基于标准 PQ 定义）：float32 原始表示 `4d` 字节 → PQ 表示 `m` 字节，压缩比约 `4d / m`；例如 `d = 768`、`m = 96` 时约 32 倍。

距离计算用**非对称距离计算（ADC）**：查询向量保持全精度，预先为每个子段、中心计算查询与该中心的距离，存入 `m × 256` 的查找表；扫描时对每个候选编码逐字节查表求和。这把每次距离计算从 `d` 次乘加降到 `m` 次查表加法。

精度损失的来源（基于 PQ 定义推导）：一是**子空间独立假设**，各段独立量化忽略了跨子空间的协方差，相关性强的维度被分到不同段时误差会叠加；二是**中心数有限**，每段通常 256 个中心，量化是"就近取代表"，实际距离被近似；三是 **`m` 的权衡**，`m` 越大每段维度越小、量化误差越小，但编码变长、查找表变大，且 `m` 必须整除 `d`。因此 PQ 的典型定位是**粗排**：用压缩向量拿到较大的候选集（如数百到数千），再用全精度向量或交叉编码器精排。量化原始论文的链接未取得，此处不引用。

#### 4.6.3 DiskANN

设计取向：把图索引与全精度向量放在 SSD 上，内存中只保留压缩后的向量（如 PQ 编码）用于**粗筛**，再用束搜索批量读取 SSD 上的邻居节点，用 IO 合并摊薄磁盘随机读的成本。目标是单机在十亿级规模上做到高召回与低延迟，代价是 SSD 容量与 IOPS 要求，以及显著的工程复杂度。论文出处未取得可定位来源，此处不引用。

#### 4.6.4 暴力检索的适用边界

暴力检索（Flat / brute force，精确 top-k）在以下条件下是**正确选择**而不是妥协。向量数量在 `10^4` 量级以下、维度在数百量级时，一次全量内积的耗时通常在毫秒级（数量级估算，随硬件与实现变化）。需要 100% 召回的可验证性时（构建评估集、验证 ANN 参数造成的召回损失），只有暴力检索能给出召回上限基准。元数据过滤极其苛刻时，高选择性的过滤会让 ANN 的可用候选所剩无几，暴力 + 过滤反而更简单也更准。索引重建频繁、数据规模波动大时，维护 ANN 图结构不划算。一个实用的判据是**先测量"过滤后剩余候选数"**：如果过滤条件把候选集压到几万条以内，Flat 往往比带过滤的 ANN 更快且召回更高。

#### 4.6.5 相似度度量与归一化等价性

代数推导见 3.3 节，选型规则同那一节的四条结论：训练目标是余弦时统一归一化，metric 选 `cosine` 或 `inner product` 结果一致；范数携带语义信息的内积模型不要归一化；混用不同模型的向量前必须归一化；同一集合内表示必须统一。索引配置层面要注意的是，**归一化是写入前的约定，事后修改需要重建索引**，因此应在建库脚本里写成不可绕过的步骤，并确保查询侧做同样处理。

#### 4.6.6 索引选型速查

| 场景 | 建议 | 理由 |
| --- | --- | --- |
| 原型 / 评估集构建 / < 10^4 向量 | Flat（暴力） | 精确、零调参、可用作召回上限基准 |
| 生产，10^5–10^7，内存充足，要求低延迟高召回 | HNSW（或同类图索引） | 对数级查询复杂度、高召回区间性能好 |
| 内存受限，10^6–10^8 | IVF-PQ（或 HNSW + 量化） | 压缩换取容量；用重排补精度 |
| 需要按元数据强过滤 | 分区/多索引 + 小图索引，或对过滤后小集合用 Flat | 避免过滤破坏图连通性 |
| 10^8 以上，单机或成本敏感 | DiskANN 类磁盘驻留方案 | 内存不足以容纳图与全精度向量 |

### 4.7 过滤与元数据

元数据过滤（租户、权限、时间、文档类型、数据分级）在 RAG 里不是"附加功能"，而是**决定召回率上限的约束**。

#### 4.7.1 预过滤 vs 后过滤

| 方案 | 执行顺序 | 召回率 | 延迟 | 主要问题 |
| --- | --- | --- | --- | --- |
| 后过滤（post-filter） | 先 ANN 取 top-k，再按元数据丢弃 | **可能严重下降** | 通常很低（过滤是便宜的） | top-k 被不合法文档占满时，合法结果可能不足 k 条甚至为 0 |
| 预过滤（pre-filter） | 先按元数据选出合法集合，再在集合内 ANN | 高 | 可能很高，甚至退化 | 图索引连通性被破坏；或退化为对合法集合的暴力扫描 |
| 分区/多索引 | 按分区键路由到独立索引，索引内检索 | 高 | 低 | 索引数量膨胀、运维成本、跨分区查询需要 fan-out |
| 过滤感知的索引 | 索引内部感知过滤条件（多种实现） | 高 | 低到中 | 实现复杂、行为依赖具体产品 |

#### 4.7.2 后过滤的召回率陷阱

设过滤条件的选择性为 `s`（合法文档占比），检索 top-`k`。若过滤与相关性**近似独立**，期望返回的合法结果数约为 `k · s`。例如 `k = 20`、`s = 0.05`（多租户场景很常见），期望只剩约 1 条合法结果，且方差很大——有时为 0 条。用户看到的现象是"系统偶尔答非所问""某些租户总是查不到"。

常见的"补丁"是过采样：先取 `k' = k / s_hat`，过滤后再截断到 `k`。但这有三个前提：`s_hat` 可估计、过滤与相关性独立（**这个假设经常不成立**——例如"最新文档"这类过滤与查询意图天然相关）、候选集大小上限可控。假设不成立时，过采样既浪费延迟又不解决问题。

#### 4.7.3 预过滤的代价：图连通性破坏

HNSW 的搜索是在图上做贪心游走。当过滤条件把大部分节点排除后，**图上大量边指向非法节点**，游走会陷入一个由合法节点构成的稀疏不连通子图，表现是召回下降（找不到本该可达的合法邻居）与延迟上升（需要更大的 `efSearch` 才能补偿）。IVF 类结构受影响较小，因为"只在合法的倒排桶内扫描"天然就是预过滤。

| 过滤选择性 | 建议做法 | 理由 |
| --- | --- | --- |
| 高（合法占比很低，如单租户权限、数据分级） | 分区/独立索引 | 避免在共享大索引里过滤 |
| 中 | 过滤感知的索引实现，或适度提高 `efSearch` | 用延迟换召回 |
| 低（几乎全通过，如时间范围很宽） | 后过滤即可 | 过滤便宜且几乎不损失召回 |

#### 4.7.4 多租户隔离

| 方案 | 隔离强度 | 成本 | 召回风险 | 适用 |
| --- | --- | --- | --- | --- |
| 单集合 + `tenant_id` 过滤 | 逻辑隔离，依赖查询构造正确 | 最低 | 过滤选择性高时召回下降；查询漏加租户条件会造成**跨租户数据泄露** | 租户数多、单租户数据小 |
| 每租户一个集合/索引 | 物理逻辑双重隔离 | 高（索引数膨胀、内存碎片） | 无 | 租户少、数据敏感、合规要求高 |
| 分区（partition key）路由 | 逻辑隔离 + 路由隔离 | 中 | 低 | 租户数量中等 |
| 独立部署/独立库 | 最强 | 最高 | 无 | 数据敏感度最高的租户 |

必须强调的三点约束。**租户条件必须在服务端强制注入**，不能依赖调用方传参——任何"客户端传 `tenant_id`"的设计在提示注入或接口被直连时都会失效。**检索结果的引用内容与元数据同样敏感**：即使只返回文本片段，片段本身已是数据泄露。**过滤必须发生在召回层**，不能靠"生成模型不要提别的租户"，生成层不可信。这三条是工程规范层面的判断，不建议只依赖某一产品的默认行为。

#### 4.7.5 元数据设计

| 字段类别 | 例子 | 用途 |
| --- | --- | --- |
| 身份/权限 | `tenant_id`、`acl_group`、`classification` | 强制过滤，安全边界 |
| 来源定位 | `doc_id`、`source_uri`、`chunk_seq`、`title_path` | 引用展示、父子分块、结果去重 |
| 检索提示 | `doc_type`、`language`、`code_path`、`section_level` | 路由到不同索引或加权 |
| 时效 | `created_at`、`updated_at`、`valid_from/to` | 时间过滤、陈旧内容降权 |
| 质量 | `source_trust`、`is_archived` | 排序加权的先验 |

设计原则：**凡是需要用来过滤的字段，都应当在索引结构里被原生支持**（位图/倒排/分区键），而不是只存在 JSON 负载里等检索后再计算。
