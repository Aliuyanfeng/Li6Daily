## 三、离线链路——从原始文档到可检索索引

离线链路的目标只有一个：把"人写的文档"变成"检索单元 + 索引"，并让这个过程可重跑、可版本化、可增量。这条链路里每个环节的错误都会被在线检索放大，且无法在检索层补救——检索单元缺失的信息，没有任何重排模型能从排名里恢复。

### 3.1 文档解析与清洗

解析层的产出不是纯文本，而是**带结构的文本 + 元数据**。结构一旦在解析阶段丢掉（标题层级、表格边界、代码围栏、列表从属关系），后面的结构感知切分就无从谈起。解析选型的第一条判据因此是"能不能保留层级与块类型"，而不是"能不能提取文字"。

| 格式 | 解析要点 | 常见噪声 | 处理方式 |
| --- | --- | --- | --- |
| Markdown | 保留 ATX 标题层级、代码围栏、列表缩进 | 内嵌 HTML、多余空行、参考式链接残留 | 记录标题路径；围栏内文本不参与正文切分 |
| HTML | 按标签语义抽取正文，保留 `h1`–`h6`、`table`、`pre` | 导航、页脚、脚本样式块、Cookie 提示 | 先剥模板，再按标签结构切分 |
| PDF | 抽取文本流并按字号/字体恢复标题层级 | 页眉页脚、分栏错序、断行连字符 | 按页与版面块重组；页眉页脚按重复模式剔除 |
| Office 文档 | 按段落、工作表、幻灯片三种粒度处理 | 修订记录、批注、隐藏行、合并单元格 | Excel 按"表"为单元，每行补表头后转键值文本 |
| 纯文本/日志 | 按行扫描，识别模板行 | 时间戳与请求 ID 造成的高相似重复行 | 模板去重，时间戳与关键字段提升为元数据 |
| 源码 | 按 AST 抽取函数/方法/类定义 | 注释与实现分离、嵌套结构、多行签名 | AST 级切分，块头注入文件路径与签名 |

清洗要区分两类操作。**无害归一化**包括统一换行符与编码、合并连续空行、剥除零宽字符。**有损归一化**必须慎用：把 `0x` 前缀、编号里的连字符、版本号里的点号、路径里的分隔符统一掉，会直接破坏字面匹配能力。判断标准是——**如果这个字符模式本身是被检索的对象，就不能归一化它对检索可见的形式**。

解析阶段就该写死的元数据：文档 ID、来源 URI、标题路径、块序号、文档类型、语言、创建与更新时间、访问控制组。这些字段既要用于引用展示，也要用于过滤与去重，晚补的代价是重建索引。

### 3.2 切分策略

切分决定了"检索单元"是什么。上游切分错了，下游任何重排、任何索引优化都救不回来。Anthropic 在其上下文检索的实现说明中把"块边界"列为第一项注意事项，明确指出块大小、块边界与块重叠都会影响检索效果（来源：Anthropic，*Introducing Contextual Retrieval*）。

#### 3.2.1 四种切分策略对比

| 策略 | 边界依据 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| 固定长度 | 字符/token 计数 | 实现最简单、块长可控、吞吐高 | 任意位置截断，可能切断句子、表格行、代码块、标题与内容的从属关系 | 日志、纯文本流水、作为基线 |
| 递归字符 | 按分隔符优先级递归下降 | 尊重段落/句子边界，块长仍有上界 | 不理解语义与结构层级；表格与代码仍会被切坏 | 通用正文的默认选择 |
| 语义切分 | 相邻句/段的 embedding 相似度下降处断句 | 边界更贴近主题转换 | 需额外一次 embedding 前向（全量语料 × 句子数）；阈值难标定；不保证块长上界 | 主题漂移明显、段落冗长的文档 |
| 结构感知 | 文档结构（Markdown 标题层级、HTML 标签、代码 AST/函数定义） | 检索单元与语义单元一致，可附带层级路径元数据 | 需按格式分别实现；结构不规范的文档退化 | 技术文档、规范、代码库（RAG 场景收益最大） |

递归切分的源头是 LangChain 的 `RecursiveCharacterTextSplitter`（master 分支，未固定版本）：默认分隔符顺序 `["\n\n", "\n", " ", ""]`，长度超限时按下一个分隔符继续递归；`from_language` 为各语言提供专用分隔符表（来源：LangChain 源码 `character.py`）。Markdown 优先按 `\n#{1,6} ` 切、其次代码围栏与水平线；Python 按 `\nclass `、`\ndef `、`\n\tdef ` 切，再退到 `\n\n`、`\n`、` `、空串；Go 按 `\nfunc `、`\nvar `、`\nconst ` 起始，再退到 `\nif `、`\nfor `、`\nswitch `、`\ncase `。这些是"按行首模式切"的启发式，**并非 AST 解析**；函数/方法级切分必须走 AST（Python 的 `ast`、Go 的 `go/parser` 或 tree-sitter），差别在工程上很大——行首模式切分会把多行签名、嵌套闭包、字符串拼接切坏。

#### 3.2.2 chunk size 与 overlap 的权衡

权衡本质是三个相互冲突的目标。检索精度要求块小：块越小，向量越"单一主题"，相似度信号越干净，但上下文越不完整。生成完整性要求块大：块越大，越可能包含回答问题所需的完整上下文（定义、前提、例外条件），但噪声也更多。成本与延迟要求块大：块数越少（索引更小、检索更快），但每块 embedding 更贵、占用的上下文窗口更多。

关于"业界常见区间"，只给有来源的锚点。Anthropic 描述传统 RAG 流程时写了"把语料切成小块，通常不超过几百 token"；同一篇文章的成本估算使用 **800 token 块、8k token 文档、每块 50–100 token 上下文前置**这组配置，并给出一次性生成上下文化的成本约 **每百万文档 token 1.02 美元**（来源：Anthropic，*Introducing Contextual Retrieval*）。至于"256/512/1024 之类具体默认值"，素材未取得可定位来源，此处不引用——这类值依赖模型的最大输入长度与语料性质。

| overlap 的作用 | 机制 | 代价 |
| --- | --- | --- |
| 防止答案被切在边界上而两边都不完整 | 相邻块共享一段文本 | 索引体积与 embedding 成本按 overlap 比例线性上升；同一内容被多次召回，需要去重，否则浪费上下文预算 |
| 提高边界处事实被完整覆盖的概率 | 同上 | 相似度检索中重叠内容会互相竞争排名，可能出现"同一段话占满 top-k"的现象 |

更精确的做法是把 overlap 当作**去重与合并问题**处理，而不是"多切一点就完事"：对同一父文档的多个命中块做相邻合并（连续块拼接后再送给生成），比盲目提高 overlap 更省上下文。

#### 3.2.3 父子分块（small-to-big）

机制是解耦：用**小块**（child）建索引用于检索，命中后送出**大块**（parent，如所在小节或整篇）给生成模型。这样"检索需要的高信噪比"与"生成需要的完整上下文"不再互相妥协。

| 变体 | 检索单元 | 返回单元 | 关键要求 |
| --- | --- | --- | --- |
| Parent-Child | 子块 | 父块（小节/整文档） | 需存储父子映射；父块大小要受上下文预算约束 |
| Sentence-Window | 单句（或小窗口） | 命中句 + 前后 N 句 | 需保存句子级顺序与文档偏移；适合"事实密集、答案是一句话"的语料 |
| Small-to-Big（相邻扩张） | 小块 | 小块 + 左右邻居块 | 实现最轻，等价于检索后用 overlap 扩张 |

新问题是**父块膨胀导致上下文预算被一两个命中占满**。实践中需要用配额控制：每文档最多贡献 N 个块、父块总 token 上限、命中同一父块的多个子块只计一次。这几项必须显式设默认值，否则线上会稳定地由最长的父块把上下文吃光。

#### 3.2.4 上下文预置（Contextual Retrieval）

问题定义很准确：传统切分**破坏了上下文**。Anthropic 举的例子是一个金融文档块"公司营收环比增长 3%"——单独看它不知道是哪家公司、哪个季度，因此既难被检索到，也难被正确使用。

做法：在 embedding 与建 BM25 索引**之前**，用 LLM 为每个块生成一段简短的、依附于整篇文档的说明性上下文，并前置到块上。Anthropic 公开了其提示词结构：把整篇文档与待定位的块一起给模型，要求输出"一小段把该块定位于整篇文档中的上下文"，且只输出该上下文，生成结果通常 **50–100 token**（来源：Anthropic，*Introducing Contextual Retrieval*）。

成本侧的关键机制是 **prompt caching**：参考文档放进缓存一次，后续块复用缓存内容，不必为每个块重复传递整篇文档；在上述假设下一次性生成成本约每百万文档 token 1.02 美元（来源同上）。这是"离线一次性成本换在线召回率"的典型形态。

效果（Anthropic 多领域实验，指标为 `1 - recall@20`，来源同上）：

| 配置 | top-20 召回失败率 | 相对基线降幅 |
| --- | --- | --- |
| 基线（仅 embeddings） | 5.7% | — |
| + Contextual Embeddings | 3.7% | 35% |
| + Contextual Embeddings 与 Contextual BM25 | 2.9% | 49% |
| 再加重排模型 | 1.9% | 67% |

同文还给出三条与召回层直接相关的观察：知识库小于约 20 万 token（约 500 页）时可以直接全量放进提示词而不必做 RAG；送入 5/10/20 个块时，其实验中 20 个表现最好；上下文增强的收益可与其嵌入模型选择、重排、块数选择**叠加**（来源同上）。

实现上要注意：前置上下文会**改变块的长度分布**（每块 +50–100 token），因此父块配额、上下文预算、"每文档最多几块"都要跟着重算；前缀还会稀释块尾内容的向量权重，长块更明显。

#### 3.2.5 长文档、表格、代码的特殊处理

| 对象 | 主要失败模式 | 处理策略 |
| --- | --- | --- |
| 长文档（规范、手册） | 单块无法覆盖完整论证；跨节引用丢失 | 结构感知切分 + 每块附"标题路径"元数据（如 `产品/模块/子节`）+ 父块返回 |
| 表格 | 行被切断、表头与数据分离导致数值无意义；Markdown 表格在向量空间里语义稀薄 | 整表不切分或按行组切分；**每块重复表头**；把表转成"键: 值"或自然语言描述（`列名=值` 的逐行文本化）；表格单独建索引或作为父块 |
| 代码 | 函数被截断、注释与实现分离、import 关系丢失 | AST 级按函数/方法/类切分；块头注入文件路径、包名、签名；对跨文件调用关系另建图或按 repository × path 过滤 |
| 日志 | 高度重复的模板行导致向量空间中大量近似重复点 | 先去模板化/归一化，块内保留时间戳与关键字段作为元数据；这类语料对 BM25/字面匹配的依赖更强 |
| 版本号与编号类短文本 | 行短、语义稀薄、分词器容易切碎 | 保留原始字面；优先靠稀疏路召回；把编号提升为独立的可过滤元数据字段 |

对表格有一个具体提醒：如果把表格转成自然语言，务必保留**列名与行标识**，否则检索层无法区分"召回率高"和"精确率低"这两个数值。

#### 3.2.6 把切分纳入评估

切分参数（策略、size、overlap）是**可搜索的超参数**，不是"设一个业界值"就完事。做法是固定检索器与评估集，把 `(策略, size, overlap)` 作为网格或随机搜索，用 Recall@k / NDCG@k 做选择。两点约束：候选空间应当小（例如十来组），否则在**同一评估集**上迭代过多会过拟合；评估结果必须绑定语料版本与索引配置，否则历史指标不可比。一个可操作的判据是，如果优化切分参数带来的 Recall@k 提升小于噪声幅度（同一配置重跑或换评估子集的波动），就不要采纳这组参数。

### 3.3 向量化

**批处理。** 前向成本近似与 batch 大小成正比，但吞吐在某个 batch size 之后不再提升，内存占用继续线性上升。实践中取"能稳定跑满的最大 batch"的 60%–80% 作为默认值，并做成配置项而非硬编码。三个必须处理的细节：长块与短块混在同一 batch 会造成大量 padding，按长度分桶可显著提高吞吐；失败重试必须幂等，批处理中断后要能按块 ID 断点续跑；编码器版本要写进索引元数据，换了模型必须重建。

**维度。** 维度由模型决定，不支持按需裁剪——降维要用模型自带或训练过的投影，截断维度会破坏训练得到的度量结构。维度翻倍，向量体积与距离计算开销大致翻倍，压缩编码（如 PQ）的压缩比也随之变化。

**归一化。** 这是易错点最集中的一条。

```text
内积：      ⟨a, b⟩ = Σ a_i b_i
余弦：      cos(a, b) = ⟨a, b⟩ / (‖a‖ · ‖b‖)
欧氏距离：  ‖a - b‖² = ‖a‖² + ‖b‖² - 2⟨a, b⟩
```

第一，**归一化后内积等于余弦**。若 `‖a‖ = ‖b‖ = 1`，则 `cos(a,b) = ⟨a,b⟩`。因此"归一化后用内积检索"与"用余弦检索"得到**完全相同的排序**——这不是近似等价，而是数学等价。第二，**归一化后欧氏距离与余弦/内积的排序也等价**：此时 `‖a - b‖² = 2 - 2⟨a,b⟩`，欧氏距离是内积的单调递减函数。第三，**未归一化时三者会给出不同排序**：`‖b‖` 会影响内积，范数更大的向量获得更高内积，而欧氏距离同时受方向差异与长度差异影响。这正是"向量库 metric 选错会导致召回异常"的根因。由此得到四条规则：训练目标是余弦时（多数文本 embedding 属于此类），入库前统一归一化，metric 选 `cosine` 或 `inner product` 结果一致；模型训练用内积且范数携带语义信息时，不要归一化；混用不同模型的向量前必须归一化；同一集合内表示必须统一。一个容易忽略的运维后果是：**归一化是数据写入前的约定，事后修改需要重建索引**，因此应在建库脚本里写成不可绕过的步骤，并确保查询侧做同样处理。

### 3.4 索引构建与增量更新

增量更新的吸引力是写入延迟低，但代价集中在三处：删除支持、图结构退化、版本一致性。以 HNSW 为例，它的删除支持弱，常见实践是软删除（标记删除位，查询时过滤）加定期重建；软删除比例升高后，图上大量边指向已删除节点，有效连通性下降，召回随之下降——这与 4.7 节的"过滤破坏图连通性"是同一个机制。

| 维度 | 全量重建 | 增量更新 | 混合（增量 + 定期重建） |
| --- | --- | --- | --- |
| 写入延迟 | 高（需重跑全量编码） | 低 | 低 |
| 删除语义 | 直接生效 | 需软删除承载 | 重建时物理清除 |
| 长期召回衰减 | 无 | 有（软删除累积、图退化） | 可控 |
| 运维复杂度 | 低 | 低 | 中（需调度与切换逻辑） |
| 适用 | 语料小、更新批次化、模型升级 | 追加为主、删除极少 | 多数生产场景 |

实践中更稳的路径是混合方案：写入走增量，按软删除比例或数据量增长阈值触发重建，并且**重建期间新旧索引并存**，用别名切换而不是原地替换。切换必须原子，否则会出现一部分查询打新索引、一部分打旧索引的中间态。

从"文档写入"到"可检索"的延迟由链路上最慢的一环决定：解析 → 切分 → LLM 上下文预置（若启用）→ 向量化 → 写索引。上下文预置引入的是一次 LLM 调用，通常是全链路里最慢的一步，因此对实时性敏感的场景应把它放在异步流水线上，允许新文档先以无前置上下文的形态可检索，稍后再刷新并重新向量化。最后一条容易被忽视的是，**索引元数据必须能回答"这批向量是用哪个版本的切分和模型生成的"**——没有这个信息，召回异常排查会退化成猜测，也无法安全地做灰度重建。
