## 八、架构选型——向量库、编排框架与部署形态

本章回答三个互相牵连的问题：向量检索层用什么、编排层用什么、部署在哪里。三者不能分开决定——向量库的过滤能力决定检索链路怎么写，编排层的许可条款决定产品能不能对外交付，部署形态又约束向量库与模型的可选范围。

> **本章数据核实口径**：本章的许可、能力边界与定价均取自官方文档、官方仓库元数据或许可文件原文，**统一查看日期为本文整理时**。产品能力、区域与价格会随时变化，本章结论只在该时点成立，落地前应重新核对。官方页面展示价为展示值，实际以控制台结算为准。

### 8.1 向量存储与检索层选型

#### 8.1.1 专用向量库：Milvus、Qdrant、Weaviate、Chroma、Vespa

先看定位与许可，这两项决定一个产品能不能进你的技术栈。

**Weaviate 的混合许可必须单独看清楚。** 它不按"开源版 + 企业版"划分，而是按目录切分：`wl` 目录及其子目录适用企业专有许可。选型时若用到这部分能力，等于引入商业授权依赖。

索引能力上，五家的差异比定位差异更值得关注。

几条容易影响决策的补充事实 [已核实]：

Milvus 官方文档站当前版本线为 v3.0.x。Tiered Storage（数据按需从对象存储缓存到 QueryNode）自 Milvus 2.6.4 起提供。官方明确提示：未缓存数据的查询会产生额外 I/O 与更高延迟，建议冷热查询分别实测。Milvus 文档声明支持十亿级、数百亿级向量规模——这是官方声明，不是可复现基准，不能当作容量承诺。

Qdrant 的二值量化官方基准（DBpedia + `text-embedding-3`）：3072 维开启 rescore 后准确率 97%~99%，不开启为 76%~77%；512 维开启 rescore 为 71%~91%，不开启仅 53%~55%。官方建议以 3 倍 oversampling + 开启 rescore 作为起点。**低维模型叠加激进量化是最容易踩的组合**，8.1.5 节会再提。

Weaviate 的 HFresh（v1.36 引入）基于 SPFresh，仅质心索引常驻内存（8-bit 旋转量化），posting list 落盘（1-bit 旋转量化），仅支持 cosine 与 l2-squared 距离；v1.40 起支持 ColBERT / ColPali 类多向量，但须经 MUVERA 编码。其 GraphQL API 官方标注已公告未来将下线，使用者需留迁移窗口。

#### 8.1.2 传统数据库扩展：pgvector、pgvectorscale、Elasticsearch、OpenSearch、Redis

对已有 PostgreSQL、Elasticsearch 或 Redis 的团队，复用既有组件通常比引入专用向量库更省运维。但这条路的坑集中在过滤与召回上。

| 维度 | PostgreSQL + pgvector | Elasticsearch | OpenSearch | Redis（RediSearch） |
| --- | --- | --- | --- | --- |
| 许可 [已核实] | PostgreSQL License（仓库 `LICENSE` 原文） | 仓库许可字段识别为 NOASSERTION（自定义）；官网存在 "Elastic License 2.0" 页面。**具体许可组合本轮未取得 LICENSE 原文，标注未核实** | Apache-2.0（仓库元数据 `spdx_id=Apache-2.0`） | 仓库许可字段识别为 NOASSERTION；RediSearch 同为 NOASSERTION。**具体条款本轮未取得 LICENSE 原文，标注未核实** |

**pgvector 是被误用最多的一项，四条事实必须记住。** 来源为 pgvector README，标注 [已核实]：

第一，pgvector 默认是**精确**最近邻检索，即完美召回；加索引之后才转为近似检索，才会出现召回损失。这意味着"小规模不加索引"不是偷懒，而是可接受且召回最优的做法。

第二，pgvector 的过滤在**索引扫描之后**应用。若过滤条件命中约 10% 数据、`hnsw.ef_search` 为默认的 40，平均只有约 4 行命中。官方建议开启迭代索引扫描（`hnsw.iterative_scan = strict_order` 或 `relaxed_order`）缓解。这条是"按部门/权限硬过滤 + 高召回"场景的致命点，选型阶段必须实压测。

第三，多租户场景官方建议用列表分区或独立表，共享同一个近似索引会导致跨租户互相影响召回与速度。

第四，维度上限：`vector` ≤ 2000 维、`halfvec` ≤ 4000 维、`bit` ≤ 64000 维、`sparsevec` ≤ 1000 非零元素。存储开销分别为 `4×d+8`、`2×d+8`、`d/8+8`、`8×nnz+16` 字节。**2000 维上限会直接卡掉部分高维 embedding 模型**，选模型前先核对。

关于 pgvectorscale（Tiger Data 的 PostgreSQL 扩展）：本轮 [已核实] 的内容仅为 LICENSE 为 PostgreSQL License、版权归 Tiger Data。其 README 正文未取到，因此 **StreamingDiskANN 与统计二值量化（SBQ）的具体能力与基准均标注未核实**，本节不给出相关结论。

Elasticsearch 与 OpenSearch 的向量维度上限、Redis 的具体许可条款，本轮均未核实。ES 与 Redis 的许可需在使用前查阅仓库 `LICENSE` 原文自行判定：`NOASSERTION` 不等于"许可无限制"。

#### 8.1.5 六类常见误判

这六条是本素材中代价最高的部分，依据是具体核实事实而非经验之谈。

**第一，小规模盲目上分布式向量库。** Milvus 分布式依赖对象存储、消息队列与多类节点组件 [已核实]。数据量在百万级以下时，这些组件的运维成本远高于检索收益。正确顺序是先用 Milvus Standalone、pgvector 或 Qdrant 单机把检索质量做对，再谈规模。

**第二，把"过滤"当成免费能力。** pgvector 的过滤发生在索引扫描之后，选择性强的过滤会严重掉召回 [已核实]；Milvus、Qdrant、ES 有专门的过滤执行路径。若业务强依赖"按部门/按标签硬过滤 + 高召回"，应在选型阶段就压测该组合，不能只看纯向量的 QPS。

**第三，忽略召回与延迟的量化取舍。** Qdrant 二值量化在 512 维场景不开启 rescore 时准确率仅 53%~55% [已核实，同一官方基准，见 S5]。低维模型加激进量化是最容易踩的组合。

**第四，多租户共享一个大索引。** pgvector 官方明确指出跨租户共享近似索引会相互影响召回与速度 [已核实]；Milvus 与 Qdrant 均提供专门的多租户隔离机制（分区键 / 自定义分片）。

**第五，只算存储不算内存。** Weaviate 官方 HNSW 估算显示，边开销约占向量之外的 200 字节/向量，100M 向量仅边就 20 GB [已核实]。内存公式见 8.4.4。

**第六，把许可当形式。** Weaviate 的 `wl` 目录为企业专有；Dify 与 FastGPT 是修改版 Apache-2.0（禁止未授权多租户 SaaS、不得移除 LOGO）；MaxKB 为 GPL-3.0；QAnything 为 AGPL-3.0 [均已核实]。若要对外提供多租户服务或二次分发，必须在选型阶段就过一遍许可。

| 路线 | 适用条件 | 收益 | 代价 |

| 用库型框架（LangChain / LlamaIndex / Haystack） | 需要快速接多模型、多向量库；数据源格式杂 | 生态组件多；接入快 | 抽象泄漏；破坏性升级；调试链条长 |
| 用开箱平台（RAGFlow / Dify / FastGPT / MaxKB） | 业务方要自助使用；需要可视化编排；预算与人力有限 | 上手快；含文档解析与界面；运营成本低 | 定制受限于平台；许可限制（多租户 / 去 LOGO / 传染性）；深度调优难 |

组合建议 [推断]：**平台做数据接入与运营界面，自研做检索与生成链路**。用平台或框架完成解析、切分、向量化与知识库管理，把召回编排、融合、重排与生成放在自有服务中，通过平台 API 交互。这样既避免重复造文档解析的轮子，又不会被平台的检索策略锁死。

以内部代码库为例，这一组合意味着：用平台解析仓库文档、生成向量并管理知识库；代码标识符召回、BM25 与向量融合、重排顺序则全部由自研服务控制——后者恰恰是平台最难定制、也最影响效果的部分。

### 8.3 检索架构模式演进

#### 8.3.1 三阶段演进：纯向量 → 混合检索 → 带重排两阶段

| 阶段 | 结构 | 解决的问题 | 主要代价 |
| --- | --- | --- | --- |
| 纯向量检索 | 查询向量 → ANN Top-K → 生成 | 语义相似但字面不匹配的召回 | 专有名词、编号、代码标识符召回差；对精确匹配不敏感 |
| 混合检索 | 稀疏检索（BM25 / 学习式稀疏）+ 稠密检索并行 → 融合 | 精确词命中与语义命中互补 | 需要两套索引与融合权重；调参成本上升 |
| 两阶段（带重排） | 召回 Top-N（N 远大于 K）→ 交叉编码器重排 → Top-K → 生成 | 提升最终上下文的排序质量 | 重排是逐对计算，算力/延迟随 N 线性增长；引入额外模型与 GPU 或 API 成本 |

支撑事实 [已核实]：Milvus 原生支持 BM25 全文检索与学习式稀疏向量（SPLADE、BGE-M3），可在同一集合中混存稀疏与稠密向量，并通过函数对多路检索结果重排。Elasticsearch 提供 `retrievers` 组合多路检索，支持 `rrf`（倒数排名融合）与 `linear`（加权线性组合）；ES|QL 侧通过 `FORK` 并行多路、`FUSE` 融合、`RERANK` 语义重排。Qdrant 提供混合查询、稀疏向量检索、多向量（ColBERT 类）后期交互检索，以及 FastEmbed 侧的重排器与多向量后处理。Vespa 官方文档的排序章节独立包含交叉编码器重排与 searcher 内重排。OpenSearch 文档目录包含重排序（Cohere Rerank、Bedrock、SageMaker 交叉编码器、按字段重排）与生成式 AI 教程。

#### 8.3.2 多路召回与融合：RRF

融合算法优先用 RRF（倒数排名融合）。已核实公式（Elasticsearch 官方文档，并给出论文链接 Cormack et al., SIGIR 2009）：

```
score(d) = Σ_q  1 / (k + rank(result(q), d))     # 仅当 d 出现在 result(q) 中
```

`k` 为排名常数，ES 中 `rank_constant` 默认 60。`rank_window_size` 决定每路子查询参与融合的结果集大小；ES 明确说明**改变 `rank_window_size` 会改变最终排序**，因此分页时必须保持该值不变，否则跨页结果可能重复或丢失。ES 同时说明 RRF 无需调参、各相关性指标不必同源，相比线性加权在多数场景给出更好的相关性；也列出 `rrf` retriever 不支持 `scroll`、`sort`、`rescore`。

工程要点 [推断]：每路召回先用较大的 `rank_window_size`，融合后再截断到 `size`。融合优先用 RRF（免调参），只有具备评测集且证据充分时才上线性加权。多路召回的"路"应覆盖不同的召回失效模式：稠密向量负责语义，BM25/稀疏负责精确词、编号与代码标识符，结构化过滤负责权限、时间与租户。重排放在融合之后，对融合后的 Top-N 做交叉编码器打分——顺序反了会放大成本。

#### 8.3.3 朴素 RAG / 高级 RAG / 模块化 RAG

[推断] 三者不是互斥的技术栈，而是**能力递进的组织方式**。

朴素 RAG 是固定链路：切分 → 向量化 → Top-K → 拼接 → 生成。适合作为基线，必须先跑通并建立评测集。高级 RAG 在固定链路的各环节加优化——查询改写/多查询、混合检索、重排、上下文压缩、迭代检索，本质上仍是"一条链路"。模块化 RAG 把链路拆成可插拔模块（索引、检索、融合、重排、生成、路由、记忆），按查询类型动态编排，适合查询类型明显异构（事实型 / 全局型 / 多跳型）的系统。

工程建议 [推断]：先有评测集，再逐项加模块；每加一个模块都要有"该模块带来的评测指标提升不小于其延迟与成本增量"的证据。以客服工单场景为例，工单文本短、查询多为具体报错信息，混合检索的收益通常远大于模块化编排；反过来，法务合同场景的长文档归纳查询才需要模块化路由。**没有评测集的"高级 RAG"改造无法判断是否有效。**

#### 8.3.4 GraphRAG 与 Agentic RAG 的适用边界

| 模式 | 解决的问题 | 值得用的场景 | 过度设计的信号 |
| --- | --- | --- | --- |
| GraphRAG | 全局型问题（"这批资料的主要主题是什么"）——本质是面向查询的摘要任务，而非显式检索任务 | 语料内部实体关系强、需要跨文档归纳；问题常为全局性、总结性 | 语料以独立文档为主、问题以局部事实型为主；无预算做实体与社区摘要的构建与增量更新 |
| Agentic RAG | 多跳、需要工具调用与自我纠错的查询 | 查询路径不确定、需要外部工具或多次检索验证 | 单跳事实问答占比高；延迟预算紧张；检索质量本身还没做对 |

已核实支撑事实（arXiv:2404.16130）：GraphRAG 由微软提出，用 LLM 分两阶段构建图索引——先从源文档抽取实体知识图，再为紧密相关实体群预生成社区摘要；回答时每个社区摘要生成部分回答，最后汇总。论文报告在约百万 token 级数据集上，对全局性"意义构建"类问题的答案全面性与多样性相比常规 RAG 基线有显著提升。这是论文自报结果，迁移到自有语料上未必复现。

[推断] 边界判据：GraphRAG 的成本主要在**索引期的 LLM 调用**（实体抽取 + 社区摘要），且语料更新需要增量重建；Agentic RAG 的成本主要在**查询期的多次 LLM 调用与工具往返**（延迟与 token 双增）。若语料更新频繁而查询量不大，GraphRAG 的索引成本可能高于其收益；若查询量大而检索质量本就够用，Agentic RAG 会放大延迟与成本。

一句话判据：**问题形态决定要不要上，更新频率与查询量决定上不上得起**。医疗问答这类语料更新慢、存在跨文档归纳需求的场景，GraphRAG 相对有账可算；电商商品库这类高频更新、以局部事实查询为主的场景，两者都属于过度设计。

### 8.4 部署形态与成本

#### 8.4.1 三种部署形态

| 形态 | 组成 | 优势 | 代价 | 适用 |
| --- | --- | --- | --- | --- |
| 全私有化 | 向量库 + embedding 模型 + rerank 模型 + LLM 全部本地 | 数据不出域；合规可控；无按量费用 | 需 GPU；显存与并发须自行规划；模型效果受自托管模型能力约束；运维工作量大 | 强合规（数据不出域、行业监管要求） |
| 云 API | 向量库云托管 + embedding/rerank/LLM 均走 API | 上线快；零 GPU 运维；弹性 | 数据出境/出域风险与合规审查；按量成本随调用量线性增长；供应商锁定 | 快速验证、非敏感数据、波动负载 |
| 混合（推荐起点） | embedding 本地或向量库自托管 + LLM 走 API | 语料向量化不外出；LLM 用最强模型；成本结构可控 | 需维护本地 embedding 服务（GPU 或 CPU）；两套凭证与限流管理 | 中型企业内部知识库 |

[推断] 判据：**语料是否敏感**决定 embedding 与向量库的位置；**答案质量要求**决定 LLM 的位置。语料敏感加答案质量优先时，embedding 本地、LLM 走 API 是常见折中。

#### 8.4.2 成本项拆解

| 成本项 | 驱动因子 | 一次性 / 经常性 | 优化手段 |
| --- | --- | --- | --- |
| 向量库内存 | 向量数 N × 维度 d × 精度字节 × 副本数 + 索引图开销 | 经常性（实例规格） | 量化（SQ / BQ / PQ）、降维（Matryoshka）、冷热分层、磁盘索引（DiskANN / HFresh） |
| 向量库存储 | 原始向量 + 原始文本 + 元数据 | 经常性 | 对象存储 + Tiered Storage；索引与原文分离 |
| Embedding 计算 | 语料 token 数（一次性）+ 增量文档 token + 查询 token × 查询量 | 一次性 + 经常性 | 本地模型摊薄；Batch 接口（百炼 Batch 价为在线价 50%）；缓存查询向量 |
| Rerank 计算 | 每次查询的候选数 N × 查询量 | 经常性 | 减小 N；用轻量交叉编码器；仅在必要时开启重排 |
| LLM token | 每次请求的输入 token（含检索上下文）+ 输出 token，乘以请求量 | 经常性 | 上下文压缩、Top-K 收敛、短语料、缓存系统提示词、选合适档位模型 |

| 网络与出口流量 | 跨区调用、对象存储读取 | 经常性 | 同区部署；避免跨区传输 |
| 人力与运维 | 集群运维、升级、调优 | 经常性 | 优先选组件少、单机可扩展的组件；云托管换人力 |

#### 8.4.3 成本估算方法论

不要直接套总价。按下列维度逐项列式，得到量级后再决策：

```
月成本 ≈ C_vector_store + C_embed + C_rerank + C_llm + C_gpu + C_ops

C_vector_store = 实例单价(规格) × 实例数 × 副本数        # 或按托管服务计费项
C_embed        = (语料token_total + 查询数 × 平均查询token) / 1000 × embedding单价
C_rerank       = 查询数 × 候选数N × rerank单价(按对/按千token折算)
C_llm          = 查询数 × (输入token × 输入单价 + 输出token × 输出单价) / 1000
C_gpu          = GPU实例单价 × 卡数 × 时长（自托管模型时）
C_ops          = 人力工时 × 人力单价 + 监控、备份与运维保障
```

配合约束 [推断]：**一次性成本**包括语料全量 embedding 与索引构建（含 GPU 时长）；**经常性成本**包括查询侧 embedding、rerank、LLM token、向量库实例、增量语料 embedding。**成本敏感度排序**（多数 RAG 系统的经验分布，需用自身数据验证）为 LLM token > 向量库规格 > rerank > embedding，查询量增长时前两项放大最快。**先算单价再算总量**：测出每次查询平均消耗的 token 数、rerank 对数与向量库 CPU，再乘查询量；缺这一步的估算误差通常超过一个数量级。

#### 8.4.4 容量规划：内存占用估算

基础公式（字节）：

```
原始向量存储
  float32:  N × d × 4
  float16:  N × d × 2
  binary :  N × d / 8
  pgvector: vector 4d+8 ; halfvec 2d+8 ; bit d/8+8 ; sparsevec 8×nnz+16

HNSW 图开销（Weaviate 官方估算口径）
  边 ≈ 10 字节 × 连接数（官方示例取 20 连接）= 200 字节/向量
  节点 = 4 字节 × d

总内存 ≈ N × (向量字节 + 边字节) × 副本数 + 服务开销 + 原始文档/元数据缓存
```

官方实测量级 [已核实，Weaviate 文档]：

| 组成 | 单向量规模 | 1M 向量 | 100M 向量 |
| --- | --- | --- | --- |
| 节点（4B × d） | 2–12 kB | 2–12 GB | 200–1200 GB |
| 边（10B × 20 连接） | 200 B | 200 MB | 20 GB |

节点一列随维度在 2–12 kB 间浮动：100M 向量时节点内存跨度达 200 GB 到 1200 GB，维度对容量的影响在千万级之后不可忽略。

量化压缩比 [已核实]：

| 方案 | 压缩比 | 来源 | 代价 |
| --- | --- | --- | --- |
| Qdrant 标量量化（float32 → uint8） | 4× | Qdrant 量化文档 | 官方称误差通常 < 1% |
| Qdrant TurboQuant bits4（默认） | 8× | Qdrant 量化文档（v1.18.0 引入） | 官方称与标量量化召回与速度相近 |
| Qdrant 二值量化 1 bit | 32× | Qdrant 量化文档（v1.5.0 引入） | 需高维且中心化分布；低维损失显著，需 rescore |
| Qdrant 乘积量化 | 最高 64× | Qdrant 量化文档（v1.2.0 引入） | 非 SIMD 友好，较慢；有精度损失 |
| Elasticsearch BBQ / int8 / int4 | 见官方文档 | ES `dense_vector` 量化章节 | 小精度损失换内存与速度 |
| Weaviate HFresh（质心 8-bit RQ + posting list 1-bit RQ 落盘） | 内存仅质心索引 | Weaviate 向量索引文档（v1.36 引入） | 仅支持 cosine / l2-squared；非峰值 QPS 场景 |
| pgvector 索引半精度 / 二值量化 | halfvec 减半；binary 大幅压缩 | pgvector README | 二值量化后需按原始向量重排以恢复召回 |

盘算示例 [推断，用上述公式自算，非官方数字]：1000 万条 768 维 float32 向量、单副本、HNSW：

```
向量: 10^7 × 768 × 4        ≈ 30.7 GB
边  : 10^7 × 200 B          ≈ 2.0 GB
合计 ≈ 32.7 GB × 副本数 + 服务开销
若改用 8× 量化（bits4）     ≈ 3.8 GB + 2.0 GB ≈ 5.8 GB
```

这个示例有两点含义：量化能把向量内存压缩近一个数量级；但边的 2.0 GB 不随量化下降，小规模时占比不高，百亿级时须单独规划。

其他容量边界 [已核实]：pgvector 非分区表单表默认上限 32 TB；索引不必全部驻留内存，但官方明确"能放内存时性能更好"，可用 `pg_relation_size` 查索引体积。Milvus Tiered Storage（2.6.4+）按需从对象存储缓存数据以降低本地资源占用，但未命中缓存的查询有额外 I/O 与更高延迟。

### 8.6 本章小结

向量层的选择顺序：先确认过滤能力是否满足业务硬约束，再看规模是否真需要分布式，最后算内存与成本。pgvector 的"过滤在索引扫描之后"与 2000 维上限、Qdrant 量化不开 rescore 的召回损失、Weaviate 的 `wl` 专有许可，这三项最容易在选型期被忽略、在后期最难返工。

编排层的选择顺序：先过许可，再定自研与平台的边界。Dify 与 FastGPT 的修改版 Apache-2.0 约束的是交付形态，不是内部使用；MaxKB 的 GPL-3.0 与 QAnything 的 AGPL-3.0 对闭源交付有实质约束。长期维护的系统里，平台做接入、自研做检索风险最低。

架构模式上，混合检索与重排的收益确定，模块化编排与 GraphRAG / Agentic RAG 的收益取决于问题形态。后两步的前提是先有评测集——没有评测集，任何"高级 RAG"改造都无法判断是否有效。
