UDP 协议概述 ​

UDP（User Datagram Protocol，用户数据报协议）是 TCP/IP 协议族中传输层的两个核心协议之一，与 TCP 并列。它在 IP 协议（网络层）之上提供无连接、不可靠、尽最大努力交付的数据报传输服务。

UDP 的设计目标非常纯粹：尽可能快地转发数据，把可靠性、流量控制、拥塞控制等职责全部交给应用层。因此它在实时性要求高、能容忍少量丢包的场景中不可替代。

UDP 的主要特点 ​

  • 无连接：发送数据前不需要建立连接，也不维护连接状态，发送结束也不需要释放连接。每台主机可以同时向多个接收方发送，也允许接收多个发送方的数据（支持一对一、一对多、多对一、多对多）。
  • 不可靠交付：不保证数据报一定能到达、不保证按序到达、不保证只到达一次。没有确认、重传、序号机制。
  • 面向报文：UDP 对应用层交下来的报文既不合并也不拆分，保留报文边界。一次发送对应一次接收（接收方 recvfrom 一次拿到一个完整数据报）。应用层需要自己控制合适的报文大小。
  • 没有拥塞控制：无论网络是否拥塞，UDP 都以恒定速率发送。这既是优点（低延迟）也是隐患（可能加剧网络拥塞）。
  • 首部开销极小：固定只有 8 字节（TCP 首部至少 20 字节），无连接状态，处理简单，传输效率高。

UDP 校验和与伪首部 ​

UDP 的检验和是可选的（IPv4 下字段为 0 表示未计算；IPv6 下校验和强制必须计算）。它采用与 TCP 相同的二进制反码求和算法。

计算校验和时，除了 UDP 首部和数据，还会拼上一个伪首部（Pseudo Header）。伪首部并不真实传输，仅用于校验，目的是让 UDP 能校验「数据报是否送到了正确的主机和协议」：

UDP 为什么是不可靠的 ​

UDP 之所以「不可靠」，是因为它在协议层面刻意不做以下事情：

  • 无确认机制：发送方发出数据报后不会等待接收方确认，也无从得知对方是否收到。
  • 无重传机制：数据报丢失、重复、乱序时，UDP 不会重发，也不做纠正。
  • 无流量控制：发送方不考虑接收方缓冲区是否溢出，可能「发爆」接收方。
  • 无拥塞控制：网络拥塞时 UDP 仍按原速率发送，可能雪上加霜。

这些「缺失」并非缺陷，而是设计取舍：换来了极低的首部开销和最低的延迟。可靠性如果需要，就由应用层协议自己实现（见下文）。

UDP 适用场景 ​

场景原因
实时音视频（直播、通话、会议）容忍少量丢包，但无法容忍重传带来的几百毫秒延迟
实时游戏 / 多人竞技延迟敏感，丢包比卡顿更可接受
广播 / 组播TCP 是点对点连接，UDP 天然支持一对多
海量小请求（DNS、DHCP 查询）一次请求一次响应，建连开销不划算
高速内网传输（如 TFTP、数据库同步）链路质量好，可靠性由应用保证更高效
需要自定义可靠性的场景应用层可在 UDP 上实现比 TCP 更贴合业务的可靠机制（如 QUIC、KCP）

基于 UDP 的典型应用协议 ​

  • DNS（域名解析）：通常基于 UDP 53 端口，一次查询一次响应，超时后才可能走 TCP。
  • DHCP（动态主机配置）：客户端初始没有 IP，无法建立 TCP 连接，只能用广播 UDP。
  • TFTP（简单文件传输）：基于 UDP 的轻量文件传输，自己实现简单确认重传。
  • SNMP（简单网络管理）：网络设备监控，UDP 161/162 端口。
  • RIP（路由信息协议）：基于 UDP 520 端口的距离矢量路由协议。
  • RTP / RTCP（实时传输协议）：音视频流媒体载体，常与 UDP 配合。
  • QUIC（HTTP/3 的底层）：在 UDP 之上实现可靠、有序、0-RTT、拥塞控制，取代 TCP+TLS。

UDP 上如何实现「可靠传输」 ​

当应用确实需要可靠，但又想保留 UDP 的低延迟/灵活性时，常见的做法是在应用层自己做可靠性，典型代表：

1. QUIC（HTTP/3） ​

Google 提出、现为 HTTP/3 标准。在 UDP 之上实现：

  • 可靠、有序传输（类 TCP）
  • 0-RTT / 1-RTT 连接建立（避免 TCP+TLS 的多轮握手）
  • 多路复用且无队头阻塞（每个流独立）
  • 连接迁移（切换网络 IP 变化不断连）

2. KCP ​

一种以牺牲带宽换取低延迟的可靠 UDP 方案，通过快速重传、忽略丢包率换速度，广泛用于游戏、弱网传输。

3. WebRTC / SRTP ​

实时音视频通信框架，媒体数据走 UDP（RTP/SRTP），信令走其他通道；丢包时通过前向纠错（FEC）、丢帧而非重传来保证流畅。

4. 自研可靠 UDP ​

游戏、IM 常基于 UDP 自研：加入序号、确认、超时重传、拥塞控制等子集，只保留业务需要的那部分，做到「刚好可靠」。

常见问题 ​

Q1：UDP 会粘包/拆包吗？ 不会。UDP 是「面向报文」的，保留了应用层交付的报文边界：发送方一次 sendto 对应接收方一次 recvfrom，不会合并也不会拆分。所谓「UDP 粘包」通常是应用层把多个逻辑消息塞进了一个数据报，或接收缓冲区一次读多了——但每个 UDP 数据报本身仍是独立的。

Q2：UDP 最大能发多大？ 理论上 UDP 长度字段 16 位，最大 65535 字节，减去 8 字节首部，单包数据最大 65527 字节。但受底层 MTU（以太网通常 1500 字节）限制，超过 MTU 会在 IP 层分片，分片任一片丢失整包作废，因此实际建议将数据控制在 1472 字节（1500 - 20 IP - 8 UDP）以内以避免分片。

Q3：UDP 不是不可靠吗，为什么 DNS 用 UDP？ DNS 查询通常一次请求对应一次响应，数据量小、对延迟敏感；若用 TCP 要多一次握手往返，代价过高。DNS 在响应超时会改用 TCP，且重要区传输（AXFR）本就走 TCP——即「默认 UDP 追求快，必要时退化到 TCP 保证可靠」。

Q4：如何对 UDP 做「限流/防拥塞」？ UDP 自身没有拥塞控制，若大量使用（如自研可靠 UDP、QUIC、视频推流），需在应用层实现拥塞控制（如 QUIC 自带 BBR-like 算法、KCP 的流控），否则容易把网络打满。
