RAG 完整链路与架构选型（9）评估体系 ​

九、评估体系与落地检查清单 ​

评估决定了前面八章所有调优是否可信。本章不复述指标的教科书定义，只给判断依据：什么指标能回答什么决策、指标在什么情况下会骗你、上线前必须核对什么。

9.1 为什么评估要分两层 ​

检索层的指标（Recall@k、NDCG@k）和生成层的指标（忠实度、答案相关性、答案正确率）不是同一件事。这个区分看起来是常识，但在工程实践中被系统性地违反。

最常见的错误决策来源是：用检索指标代替最终答案指标来验收链路改动。典型表现是重排模型的 NDCG@K3 提升几个点，就宣布优化有效并上线。但 NDCG@K3 只描述"候选池内相对顺序变好"，它不包含生成层是否因此给出更正确的答案。如果生成模型对无关片段本就有鲁棒性、会自行聚焦，排序改善可能完全不反映在最终答案上。

这一失败模式的结构性原因是链路的乘法关系：

端到端正确率上限 ≤ 召回层 Recall@K1 × 重排层把答案提到前 K3 的能力 × 生成层利用证据的能力
1

任何一个因子接近零，改动其他因子都不会改变上限。若 Recall@K1 只有 0.6（仅为说明乘法关系的假想数值，非实测），把重排从"无"升级到"最强"最多把上限抬到 0.6 附近，因为重排只影响条件概率，改变不了第一级没召回的文档；此时把召回率提到 0.85 的收益远大于换重排模型 [推断]。

由此得到两条落地原则。第一，验收某环节的改动，必须看它下游的指标：召回改动看重排前与生成后，重排改动看最终答案指标，生成改动看人工抽检与线上行为。第二，离线与在线指标必须并行报告：点击/采纳率、答案采纳、人工抽检通过率这些在线信号，与召回率、NDCG 之间没有自动的传递关系 [推断]。

9.2 检索侧指标 ​

设查询集合 Q，对查询 q 的相关文档集为 R_q（由标注得到），检索返回前 k 个结果为 L_q(k)。

指标公式适用场景局限
Recall@k（召回率）前 k 中被判定为相关的条数 ÷ 该查询全部相关文档数，再对所有查询取平均想控制"漏召回"上限；k 与下游可见块数对齐时最有用需要知道全部相关文档（标注成本高）；对"排在很后面但仍在 k 内"不敏感
Hit Rate@k（命中率）使 L_q(k) ∩ R_q ≠ ∅ 的查询占比二元成功/失败视角，最直观的 SLO 指标；适合快速回归只要有 1 条命中就算成功，掩盖"命中但排得很后"
MRR（Mean Reciprocal Rank）对所有查询求「1 ÷ 首个相关结果的排名」的平均只有一个正确答案的场景（FAQ、工单匹配、按订单号或产品型号查文档）只用第一个相关结果，忽略其余；对 k 之外无定义
NDCG@kDCG@k / IDCG@k，其中 DCG@k = Σ_{i=1..k} (2^{rel_i} - 1) / log2(i + 1)；IDCG@k 为最优排序下的 DCG相关度有等级（如 高/中/低）时最合适；能同时反映"漏"和"排错位置"需要分级标注；不同查询的 IDCG 差异大时平均值需谨慎解读
Precision@k前 k 中被判定为相关的条数 ÷ k上下文预算紧张、块数有限时（送入生成的每一块都要有用）与 Recall@k 权衡；k 固定时对相关文档总数不敏感
MAP@k各相关位置精度值的平均需要单一综合分数做 A/B 比较对分级相关度不敏感

指标选择的工程判据 [推断]：

  • 选择哪个 k，由下游决定：生成阶段能看到多少块，k 就取多少。Anthropic 用 1 - recall@20 作为指标，正是因为其配置是把 top-20 块送入生成 [已核实]。脱离下游配置选 k，指标就没有决策意义。
  • 漏召回代价高时优先 Recall@k：把 Recall 作为内部调优指标，把 Hit Rate 作为对外 SLO。反过来，上下文预算紧张时应关注 Precision@k，而不是无条件拉高召回。
  • 分级相关度 + 位置敏感选 NDCG@k：例如"现行版本文档"与"已被替代的历史版本文档"应当分级，而不是都算作相关。
  • 不要只看均值：按语言、文档类型、租户、查询长度分域报告。MTEB 的核心结论——没有单一方法在所有任务上占优 [已核实]——在内部评估中同样成立。

指标必须与代价一起看：召回率可以靠延迟换来（放宽 efSearch、扩大候选数、启用查询改写），因此应把 P95/P99 延迟与召回率画在同一张调优图上。

9.3 生成侧指标 ​

Es 等，Ragas: Automated Evaluation of Retrieval Augmented Generation，提出面向 RAG 流水线的无参考（reference-free）评估框架，即不依赖人工标注的 ground truth [已核实]。论文给出的评估维度表述是：检索系统识别相关且聚焦的上下文片段的能力、LLM 忠实利用这些片段的能力、以及生成内容本身的质量。论文编号：arXiv:2309.15217。

需要明确一处证据边界：该论文摘要没有逐项列出具体指标名称与定义。社区常用的 faithfulness（忠实度）、answer relevance（答案相关性）、context relevance（上下文相关性）等命名，以及这些指标在不同实现版本中的定义差异，本次未在论文摘要中逐项核实 [未核实]。若要在内部规范中引用具体指标定义，应直接查阅所用版本的官方文档，并以该文档为准。本节下文提到这些名字时，指的是"社区通行命名"，不是论文原文定义。

工程上的使用要点 [推断]：

  • 无参考指标适合做回归监控（版本迭代是否退化）与粗筛，不能替代需要 ground truth 的答案正确率评估；其绝对值不具跨系统可比性。
  • 判定依赖 LLM，因此继承了 LLM 判定的所有偏差（见 9.4）。
  • 指标之间必须一起看，单一指标很容易被"优化"（见 9.6）。

仅有忠实度与相关性不足以验收 RAG 系统，建议补上以下维度。

维度定义判定方式为什么必要
答案正确率与标准答案/事实一致人工或 ground truth忠实不等于正确
检索侧正确率召回片段中事实正确的比例人工标注幻觉率的上限
引用正确率引用能否支持对应断言覆盖层/蕴含层校验格式正确不代表语义正确
拒答正确率该拒答的拒答了、不该拒答的没拒构造"库外问题"负样本拒答率与误答率需同时看
格式合规率结构化输出可解析比例程序校验影响下游集成
成本与延迟每请求 token 成本、P50/P95/P99 延迟埋点与质量做联合优化

其中"检索侧正确率与生成侧忠实度同时报告"值得单独强调：答案出错时，这两个数字能直接区分"检索错了"与"模型说错了"。

9.4 LLM-as-Judge 的可靠性 ​

当评估需要"判断质量"而非"比对字符串"时，用强 LLM 做裁判是主流做法。但它的可靠性必须被量化，而不是假设。

Zheng 等，Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena（NeurIPS 2023 Datasets and Benchmarks Track）[已核实]：

  • 系统考察了 LLM-as-a-judge 的用法与局限，明确列出位置偏差（position bias）、冗长偏差（verbosity bias）、自我增强偏差（self-enhancement bias），以及推理能力有限的问题，并提出了部分缓解方案；
  • 通过 MT-bench（多轮问题集）与 Chatbot Arena（众包对战平台）验证 LLM 裁判与人类偏好的一致性：强裁判（如 GPT-4）与人类偏好的一致率超过 80%，达到人类之间一致率的同等水平；
  • 因此 LLM-as-a-judge 被作者定位为一种可扩展、可解释的近似人类偏好的方式 [论文自报]。

论文编号：arXiv:2306.05685。注意该一致率是论文自报结果，不等于第三方复现，也不等于在你们的语料与任务上成立。

偏差类型与对策对照：

偏差/问题表现缓解措施
位置偏差系统性偏向候选的某一个位置随机化候选项顺序；对 (A,B) 与 (B,A) 各评一次，只采纳一致的结论
冗长偏差把"更啰嗦"当成"更好"长度与质量分开报告（同时记录长度与得分），或对长度做归一化
自我增强偏差裁判倾向给同族模型的输出更高分裁判模型与被评模型尽量不同源
推理能力有限需要多步判断的任务上结论不稳与规则校验并用；不把裁判当唯一真相
裁判版本漂移换裁判后分数跳变，历史不可比固定裁判版本，变更作为指标断点记录

适用边界：LLM 裁判适合相对比较（A 方案与 B 方案在同一裁判、同一提示、同一批样本上对比）与大样本粗筛，不适合作为绝对分数的唯一来源。规则能覆盖的部分不必花 LLM 的钱，而且更稳定——引用是否存在、结构化事实（订单号、SKU、版本号、参数）是否在证据中原样出现，用程序校验比用裁判更可靠。

还有一条容易被忽略的操作：用人工标注子集校准裁判。在几百条人工标注样本上测裁判与人的一致率，得到"裁判可信度"数字，再决定自动评估结论的采纳力度；没有这个数字，自动评估的分数只是没有误差棒的点估计。

9.5 离线评估集怎么搭 ​

评估集的质量决定了前面所有指标是否可信，而"随机抽几个问题试试"恰恰是最常见、也最不可信的做法。

查询来源：真实查询日志采样最有代表性，但不要照搬线上的头部长尾比例（线上头部可能占 90%，照搬会让指标被少数查询支配），应分层抽样：按频次分桶（头部/腰部/长尾）各取若干。内部专家构造适合冷启动或关键能力验证（例如"必须能检索到所有法务合同模板页"）。LLM 合成查询成本低、可覆盖少见组合，但分布与真实用户不同，不宜作为唯一来源 [推断，方法论层面]。

语料快照与版本绑定：评估集必须绑定"语料版本 + 切分参数 + 索引配置"。任何一项变了，历史指标不可比；记录不全会让后续所有对比失效 [推断]。语料更新后需重建评估集，或至少标注版本差异。

标注粒度必须与线上检索单元一致：线上返回 chunk 就标注 chunk 级；如果标注文档级而线上返回块级，指标会虚高（同一文档的任何块都算命中）。这类偏差不产生报错，只产生好看的数字。

判定池（pooling）防偏差：只用当前系统的 top-k 去标注，会把"当前系统没召回的好结果"永久标记为不相关，导致后续无法发现召回改进——改进被自己的评估集挡住了。正确做法是多个异构检索器（BM25、稠密、旧版系统）各取 top-k 取并集再标注，同时记录哪些文档从未被任何系统召回（可能永远不会被发现），并在文档中承认这一局限。

相关度分级：至少三档（高度相关 / 部分相关 / 不相关），让 NDCG 可用；同时保留一个二值判定用于 Recall。

标注一致性与规模：多人标注需先做一致性检查（双标注 + 分歧仲裁）。单个查询的相关文档数很少时，单条误标对指标影响很大，此时应报告置信区间（bootstrap 重采样是常用做法）而不是只报点估计。至于"至少需要多少条查询"，取决于效果差距的大小，本文不给未经核实的经验数值。

防泄漏与防过拟合：切分评估集（dev/test），调参只用 dev；如果语料随时间增长，用时间切分（用较早数据构建评估集）来暴露"新文档不可检索"这类问题。

固化回归集：把线上出过问题的查询（含 bad case 报告）固化为回归用例，每次改动都跑；这类用例的价值高于泛化查询。

评估集的内容构成除真实查询外，还应专门包含：

样本类型用途
答案文档 ID 标注用于检索与重排评估
参考答案标注用于生成评估，与上一项分开维护
库外问题负样本测拒答行为（该拒答的拒答了）
冲突样本多来源矛盾时，检查系统是否显式列出分歧
分域样本按文档类型、问题类型分层报告，不只看总体均值

评估流程的关键控制点：

环节要点
与线上配置一致评估时使用与线上相同的切分、索引参数、融合权重、重排模型；不一致的离线指标没有预测价值
分离召回与重排的影响分别在"召回后 top-N"和"重排后 top-k"上算指标，定位问题到底出在召回还是排序
报告候选集规模记录每路召回数量、融合去重后数量；融合指标的异常常源于候选集被截断
回归触发任何环节变更（切分、embedding、重排模型、生成模型、提示模板）都跑同一套评估集
在线对照用 A/B 与人工抽检验证，观察答案采纳率/追问率/人工抽检通过率，同时监控延迟与成本

补充一点：Ragas 类无参考框架适合做持续监控和快速迭代的补充信号，但不能替代有 qrels（人工相关度标注）的召回指标 [推断]。

9.6 指标失效模式 ​

以下是几种"指标在骗你"的情形。它们的共同特征是：指标数值变好，而系统没有变好。

现象机制对策
忠实度很高但答案无用只复述片段，不做问题所需的归纳与推理同时看答案相关性/正确率
答案相关性高但不忠实输出流畅切题，但内容无据加引用校验与断言级蕴含判定
拒答率被"优化"到很低提示放宽后模型开始硬答拒答正确率与误答率一起看
指标全部提升但用户投诉增加Goodhart 效应：把指标当目标优化，而非测量结果引入人工抽检与线上行为指标（追问率、负反馈率、复制/采纳率）
换裁判后分数跳变裁判模型或提示变更固定裁判版本，记录断点，保留人工校准集
NDCG 提升但答案不变生成层已能容错无关片段把该改动重新定位为成本优化（同质量下降 K3、省 token）
单一分域上升、总体持平或下降分域之间的此消彼长被均值掩盖按分域报告，并对关键分域单独设阈值
评估集语料版本漂移语料更新后旧指标与新语料不匹配评估集版本绑定，语料变更即触发重建

这些失效模式的工程含义是一致的：没有任何单一指标可以作为验收依据。可以据此设计验收规则：一个改动要通过，需要最终答案指标改善、且没有关键分域退步、且延迟与成本在预算内；只满足其中一条不足以上线。

9.7 上线检查清单 ​

召回层

  • [ ] 是否先建了 BM25 基线并记录了 Recall@k？（依据：BEIR 结论 [已核实]）
  • [ ] 查询里含编号/标识符/代码路径时，分词器是否把它们切碎？
  • [ ] 稠密向量入库前是否统一归一化？metric 是否与训练目标一致？查询侧是否也归一化？
  • [ ] 融合用 RRF 还是加权？若加权，归一化方式与 α 是否进入离线搜索空间？
  • [ ] 切分策略是否与文档类型匹配？表格是否重复表头？代码是否 AST 级切分？
  • [ ] chunk_size/overlap 是否有评估数据支撑？
  • [ ] 是否考虑父子分块或上下文预置？父块/上下文预算是否随之重算？
  • [ ] 多轮场景是否做指代消解？原始查询是否保留？
  • [ ] efConstruction 与 efSearch 是否分开调？是否量化过过滤后候选集规模？
  • [ ] 元数据过滤是预过滤、后过滤还是分区？高选择性过滤是否已改为分区？
  • [ ] 租户条件是否服务端强制注入？

重排层

  • [ ] 是否测过召回层的 Recall@K1？若显著偏低，是否先修召回再考虑重排？
  • [ ] 是否统计过答案文档在召回结果中的排名分布，并据此设定 K2？
  • [ ] K3 是否由上下文预算、位置敏感性、正确率拐点共同确定？
  • [ ] 重排器选型是否做过"机制—成本"对照（能否预计算、在线复杂度、候选规模）？
  • [ ] 若用 LLM 重排：是否处理了位置偏差（多次打乱 + 融合）？是否按输入与输出 token 分别计过成本？
  • [ ] 是否考虑过用 LLM 排序结果蒸馏小模型来替代在线 LLM 重排？
  • [ ] 是否把重排分当作特征喂给已有的 LTR/融合层，而不是另起一条排序链路？
  • [ ] 是否按级监控 stage-wise recall，确认答案文档没有在中途级被丢弃？
  • [ ] 组批是否按 token 预算而非条数？是否实测过分批延迟并据此估算 GPU 数量？
  • [ ] max_length 与截断策略是否有评估依据？长文档是否比较过滑窗取最大与尾部截断的最终答案差异？
  • [ ] 是否设置了每一级的超时与降级路径，并埋点统计降级请求占比？
  • [ ] 截断策略用的是固定 Top-N、绝对阈值还是相对阈值？若用绝对阈值，是否做过分数校准？
  • [ ] 缓存键是否包含模型版本、提示版本、文档版本？文档更新能否按 doc_id 失效？
  • [ ] 权限过滤是否发生在重排之前？多租户缓存是否隔离？
  • [ ] 上线决策是否基于最终答案指标（而非仅 NDCG）？是否评估过"不加重排"的对照？
  • [ ] 是否自查过"重排几乎无收益"的七类场景（语料规模小、单跳事实型查询、生成层强且 K3 大、语料高度同质、依赖精确匹配信号、通用重排模型与领域分布不匹配、延迟预算极紧），确认自己不在其中？

生成层

  • [ ] 是否在自己的生成模型上做过位置敏感性测试？片段排序策略是否有测量依据？
  • [ ] 是否做了去重？是否设置了同文档条数上限？去重前后答案正确率是否对比过？
  • [ ] 上下文预算是否显式分配，并且留出了输出预留？
  • [ ] 单片段长度是否与重排的 max_length 对齐？超长片段是否用父子分块替代？
  • [ ] 引用编号是否在组织阶段固定？服务端是否校验了引用的存在性与覆盖面？
  • [ ] 拒答规则是否具体可检验？是否同时监控拒答率与误答率？是否考虑过"先抽取证据再作答"的两阶段模式？
  • [ ] 结构化输出是提示级约束还是解码级约束？字段顺序是否干扰推理？"资料不足"是否有专门的状态码？
  • [ ] 是否把检索内容视为不可信输入？是否有指令/资料分区、来源分级与审计留存？
  • [ ] 长上下文与 RAG 的取舍是否按分场景判断，而不是一概而论？
  • [ ] 是否对"标称窗口"做过自测，得到自己的有效工作区间？
  • [ ] 幻觉问题是否先分类再定位（检索缺失 / 证据忽略 / 归因错误 / 证据冲突 / 过度概括 / 时效错配）？
  • [ ] 结构化事实（编号、版本、参数）是否做了"必须在证据中原样出现"的规则校验？
  • [ ] 多来源冲突时，提示是否要求显式列出分歧？
  • [ ] 评估是否同时报告检索侧正确率与生成侧忠实度，以便区分"检索错了"与"模型说错了"？
  • [ ] 若使用压缩：是否确认压缩形式与"引用可点击回原文"的要求兼容？压缩后是否重新测了忠实度？
  • [ ] 多轮场景是否有会话级要点结构？指代消解后的独立查询是否记录？引用编号是否跨轮隔离？

评估体系本身

  • [ ] 评估集是否多系统 pooling、粒度与线上一致、绑定语料版本？
  • [ ] 指标报告是否按分域拆分，并给出置信区间？
  • [ ] 召回率提升是否计入了延迟代价？
  • [ ] 评估集是否覆盖库外问题（测拒答）、冲突样本、以及各分域？
  • [ ] 裁判模型版本是否固定并保留了人工校准集？
  • [ ] 是否避免了用单一指标做验收？是否检查过 9.6 节的指标失效模式？
