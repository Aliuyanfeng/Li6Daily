RAG 完整链路与架构选型（1）写在前面 ​

一、写在前面 ​

1.1 这篇文章解决什么问题 ​

站内已有 RAG 工作机制详解，讲清了 RAG 的概念与五个环节（分片、索引、召回、重排、生成）。那是一篇"是什么"的文章。

这一篇是"怎么搭、怎么选"。具体回答四类问题：

问题类型本文对应章节
每一环具体怎么做，参数怎么调第三章、第四章、第五章、第六章
组件和模型怎么选，为什么这么选第七章、第八章
效果怎么衡量，改完到底有没有变好第九章
什么阶段做什么事，别一上来就过度设计第二章、第十章

本文不重复概念性介绍。如果对"向量""余弦相似度""上下文窗口"这些还不熟，建议先读上面那篇。

1.2 读者假设 ​

  • 有后端或全栈开发经验，熟悉 Python（本文示例以 Python 生态为主）或 Golang。
  • 需要自己动手搭一套 RAG 系统并长期维护，而不是只做技术调研。
  • 关心的是"这套方案在我的数据规模、我的延迟预算下能不能跑起来"，而不是论文指标。

文中原理性内容与编程语言无关，工程示例以 Python 生态为主，因为当前 RAG 生态的工具链大部分以 Python 为一等公民。

1.3 本文的证据标注约定 ​

这一节请务必先读，它决定了你怎么看待本文的每一句话。

RAG 是一个实测数据极度依赖具体语料的领域。同一个检索策略，在公开榜单上排名靠前，换到你的业务数据上完全可能失效。所以本文严格区分以下几类信息：

标记含义你应该怎么看待
来源附了可点击链接或明确出处的事实：许可协议、模型维度、官方参数默认值、论文自报数据可信，但注意来源的时间点
（常规写法）用"通常""一般""实践中"等措辞表述的工程经验是推断，不是已证实的结论，需在你自己的数据上验证
（未核实）明确标注无法取得可定位来源的内容不要直接采信，需自查
无标注的机理说明从已核实原理直接推导的部分可作推论依据

三条必须说明的边界：

  1. 引用来源 ≠ 在你自己的语料上验证过。 本文引用的榜单类结论都是跨数据集平均值。落到具体领域（行业术语密集、专有名词多、长文档多）时，排序可能完全不同。
  2. 凡是标注了"论文自报"的数字，都是论文摘要中的自我报告，不等于第三方复现结果。
  3. 本文不引用未标注基准日期的榜单分数。 模型与榜单更新很快，若后续补充榜单数据，必须同时标注数据基准日期；请不要把任何分数当作"当前最新"。

本文的目标是给你一套可判断、可验证的决策框架，而不是给你一堆"照抄就能用"的魔数。凡是没有在你自己数据上验证过的参数，都应视为待调项。

1.4 术语表 ​

全文统一使用以下术语，不再混用近义词：

术语英文 / 缩写含义
分块Chunk文档切分后得到的文本片段，是检索的最小单位
向量化Embedding把文本映射为定长稠密向量的过程
双塔Bi-Encoder查询与文档各自独立编码的检索模型结构
交叉编码器Cross-Encoder查询与文档拼接后共同编码的重排模型结构
迟交互Late Interaction保留 token 级向量、在打分时做细粒度对齐的结构（代表：ColBERT）
近似最近邻ANNApproximate Nearest Neighbor，用精度换速度的向量检索
召回Recall / Retrieval从全库中捞出一批候选，追求"不漏"
重排Rerank对召回候选重新精排，追求"排得准"
级联各级候选数K1 / K2 / K3分别表示召回候选数、重排后候选数、最终送入生成模型的片段数
倒数排名融合RRFReciprocal Rank Fusion，按排名而非分数融合多路召回结果
