RAG 完整链路与架构选型（7）模型选型 ​

七、模型选型——国内方案对比 ​

本章范围严格限定在国内：国产开源、可私有化部署的模型，以及国内云厂商提供的 API 服务。国外的 OpenAI、Cohere、Voyage、Jina 等不在本章讨论范围内，也不作为对比基线引入。

本章所有参数量、向量维度、输入长度、许可与价格，均保留素材给出的原始来源，来源编号见表下注释。抓取与查看日期统一为 2026-11-24。凡素材未能从官方来源取得的值，一律在单元格中标注「未核实」，不填推测值。价格类信息为官方展示价，以控制台结算为准。

来源的类型分三档，证据强度不同：仓库中的 config.json、sentence_bert_config.json、1_Pooling/config.json 属于一手证据；模型卡正文的参数表格属于官方声明；云厂商文档中的表格属于官方声明。本章在正文中明确区分这三档，引用规格时不要混用。

读这四张表时需要先理解三个口径，否则很容易把不同来源的数字当同一回事比较。第一是维度与精度的关系：表中的维度是模型的输出维度，也是向量库的建索引维度。维度直接决定存储与内存占用，一个 100 万条、4096 维、单精度浮点的向量集合，仅向量本身就在十 GB 量级，维度减半存储基本减半。因此「可自定义维度」在本章中不是宣传语，而是实实在在的成本开关，凡涉及它的模型，正文都会额外说明截断会带来的精度代价。第二是最大输入长度与分块策略的关系：输入长度是模型的硬上限，不是推荐值。工程上按上限长度的三分之一到二分之一切块，再叠加适量的重叠，通常比贴着上限切更稳。表中凡出现「模型卡」与「config」两个值的情况，说明模型卡声明与仓库配置文件不一致，此时应以更保守的那个值为设计依据。第三是参数量与显存的关系：参数量是权重张量的元素总数，不是运行时的显存占用。按半精度估算，权重约占参数量两倍的字节数，此外还要加上激活值、批处理带来的 KV 缓存，以及检索场景中批量编码时的中间张量。本章表格提供的是估算起点，不是部署结论。

还有一点应提前说明：本章表格记录的是 2026-11-24 这一时点的状态。模型规格、许可条款、云服务的在架与下线状态都会变动，把本章数值写进设计方案之前应重新核对来源链接。特别是许可与下线两类信息，一旦变化就会直接推翻选型结论。

一手证据与归属订正

bge-m3 的 config.json 实测值：model_type=xlm-roberta、hidden_size=1024、num_hidden_layers=24、max_position_embeddings=8194、vocab_size=250002；sentence_bert_config.json 为 {"max_seq_length": 8192}。这与外部惯例引用的「1024 维、8192 长度、MIT」一致，可用作该模型规格的核对基准。该模型对应论文为 arXiv:2402.03216；同族重排模型 bge-reranker-v2-m3 的官方模型卡亦引用该编号与 arXiv:2312.15503。

Qwen3-Embedding-8B 的 config.json 实测值：model_type=qwen3、hidden_size=4096、num_hidden_layers=36、max_position_embeddings=40960；模型卡标注 Context Length: 32k、Number of Parameters: 8B，基座为 Qwen/Qwen3-8B-Base，并附论文链接 arXiv:2506.05176。这里存在一处需要在工程中留意的差异：模型卡写 32K，而 config 写 40,960。同一现象在 Qwen3-Embedding-4B（config 40,960）与 Qwen3-Embedding-0.6B（config 32,768）上同样存在。按 32K 设计分块策略是更保守的做法；若要把实际输入推到 config 上限，须自行验证位置编码外推后的检索质量。

Conan-embedding-v2 的模型卡标注：Hidden Layer Dimension 3584、FFN 中间维 8192、上下文 32,768 tokens、非 dense 层参数量 1.48B。该仓库无 config.json（HTTP 404），因此上述数值只能按官方声明采用，无法用一手文件交叉验证。参数量单元格中的 1.48B 是模型卡口径，与常规的「总参数量」不可直接横向比较。

关于 Conan-embedding 的归属需要订正：其 HuggingFace 组织为 TencentBAC，本章据此记为腾讯，业界常被误记为网易。该组织的完整机构名称未核实；如需在对外材料中署名，请以 TencentBAC 组织页 与论文原文为准。

另外注意，「未核实」在各模型上的成因不同：bge-large-zh-v1.5、bge-base-zh-v1.5、bge-m3 以及 core-emb-8b、core-emb-2b、m3e-large 是仓库未提供 safetensors 索引；m3e-base 与 Yi-1.5-34B-Chat 是抓取连接中断；text2vec-large-chinese 是仓库返回 HTTP 401。成因不同意味着可补救程度不同，前两类通常可换一个抓取时点补齐。

从这张表可以看出开源 Embedding 已经形成了明显的几档。第一档是以 512 长度档为主的中文小模型，包括 bge-small-zh-v1.5、bge-base-zh-v1.5、bge-large-zh-v1.5、m3e-base、m3e-large、Conan-embedding-v1 与 text2vec 系列（本档为档位概览，个别模型的实际取值见上表；其中 text2vec 系列部分字段未核实）。这一档的定位是把检索跑起来，显存与推理成本都低，缺点是 512 长度对企业内部文档中的长条款、长产品说明不够用，必须切得比较碎，容易切断语义。第二档是 8192 至 32768 长度的中量级模型，包括 bge-m3、gte-multilingual-base、gte-large-en-v1.5、gte-modernbert-base、Conan-embedding-v2 与 Qwen3-Embedding-0.6B。这一档是当前私有化部署的主力，长度基本够用，参数量从一亿多到十四亿多，单张消费级显卡即可承载（该档偏大成员如 Conan-embedding-v2 建议按实际显存实测）。第三档是 4B 至 9B 的大模型，包括 Qwen3-Embedding-4B、Qwen3-Embedding-8B、Qwen3-VL-Embedding-8B、bge-multilingual-gemma2 与若干阿里系的推理检索模型。这一档的检索质量预期更高，但推理成本和部署门槛都上了一个台阶，通常只在检索质量是明确瓶颈时才采用。

另一个值得单独指出的分组是「推理式检索」。bge-reasoner-embed-qwen3-8b-0923、E2Rank-8B、GVE-7B、LaSER-Qwen3-8B 以及 core 与 UEmbed 系列都归入这一类。它们的共同特征是参数量集中在 7B 至 8B 附近，其中 bge-reasoner-embed-qwen3-8b-0923 与 E2Rank-8B 的参数量一致（均为 7,568,405,504），且都与 Qwen3-8B 基座相关。这类模型在检索前或检索中引入额外的推理或组合步骤，效果上限可能更高，但带来的延迟与成本也更高，且其中多款的多语言能力标注为「未核实」或仅标英文。对企业文档问答这类以中文为主、延迟敏感的场景，把它们作为第一选择需要额外的评测理由。

同一发布方内部的命名规律也值得留意。智源的 bge-* 系列中，-v1.5 后缀是 512 长度的中文优化版本，-m3 是多语言长文本版本，-gemma2 后缀则表示以 Gemma2 为基座。判断许可时不能只看前缀，bge-m3 是 MIT 而 bge-multilingual-gemma2 是 Gemma 许可，两者同属智源但合规路径完全不同。阿里侧的 gte-* 与 Qwen3-* 两套命名对应两条技术线，前者多为 8192 长度、参数量较小，后者多为 32K 长度、参数量较大，但两者在许可上都是 apache-2.0，选择时主要看长度需求与显存预算，不必顾虑许可差异。

阿里云百炼补充事实（一手文档）

dimensions 为可选参数，取值受限：2560 仅适用于 qwen3.7-text-embedding；2048 与 1536 仅适用于 text-embedding-v4；其余 1024 / 768 / 512 / 256 / 128 / 64 通用，默认 1024。输入为字符串时最长 128,000 token（v3.7 系列）；为字符串列表时最多 20 条，每条最长 128,000 token。output_type 支持 dense / sparse / dense&sparse，稀疏向量输出仅适用于 qwen3.7-text-embedding、text-embedding-v3、text-embedding-v4，且仅支持 DashScope 接口调用。text_type 用于区分 query / document；instruct 参数仅在 text_type=query 时生效，官方称通常带来约 1%–5% 的效果提升。

火山引擎方舟补充事实（一手文档）

在架向量模型为 doubao-embedding-vision 系列，官方定位是多模态向量化模型，可将文本、图片、视频的混合输入转换为统一向量表示。版本差异：250615 起支持稀疏向量（Sparse Embedding，仅文本输入）与视频输入；251215 起支持多向量（Multi Embedding）、自定义视频抽帧与 instructions 字段；250615 已停止新购，存量可用。dimensions 可指定稠密向量输出维度（文档示例取 1024），文档同时给出模型默认输出维度为 2048；稀疏向量为固定维度，不支持单独设置。视频 token 用量方面，单视频约在 10K–80K token 区间；max_video_tokens 取值范围 [10240, 204800]，min_frame_tokens / max_frame_tokens 用于控制单帧 token 上下限。官方特别提示：不同模型版本或 instructions 配置会改变向量空间与相似度分数，不应直接比较不同配置下的绝对分数，检索效果应以同配置下的相对排序为准。单价未核实，未在本次抓取到的页面中出现。

API 端点为 https://qianfan.baidubce.com/v2/embeddings。每个文本的输入限制按模型区分，见上表。批量限制：tao-8k 的文本数量只能为 1，其他模型不超过 16 条。多模态向量模型在该文档中标注「适用模型：暂无」，且只支持单个元素输入，不支持批量。维度与单价均未核实。

实现差异需要注意：Qwen3-Reranker-* 是交叉编码器（CrossEncoder）实现，通过 causal logits 打分，config_sentence_transformers.json 中 model_type=CrossEncoder。这意味着它不能按双编码器方式预先建立文档向量索引，每次打分都要把 query 与候选文档成对送入模型，推理成本随候选数线性增长，工程上必须先做粗召回再重排。E2Rank 系列在 HuggingFace 上同时带 feature-extraction 与 reranking 标签，属于「检索 + 重排」统一模型，接入方式与单纯的交叉编码器不同。

选重排模型时，参数量是最容易被误用的一个指标。上表中 bge-reranker-v2-m3 为 567,755,777，bge-reranker-large 为 559,891,971，两者参数量几乎相同，但前者支持 8194 长度与多语言，后者仅支持 514 长度与中英，代际差异体现在基座与训练数据而不是参数规模。同理，bge-reranker-v2-gemma（2,506,172,416）与 bge-reranker-v2-minicpm-layerwise（2,724,956,928）参数量相近，但最大输入分别是 8192 与 2048，后者适用的是候选块较短的场景。把参数量当作排序依据会在这几组里直接得出错误结论。

重排模型在 RAG 流水线中的位置决定了它的长度需求远低于 Embedding。重排的输入是原始 query 加上粗召回得到的候选文本块，候选块通常已经在切块阶段被控制在数百 token。因此交叉编码器在 512 长度下也能工作，这也是 bge-reranker-large（514 长度）仍然可用的原因。真正决定重排成本的是候选数：把候选从 100 条降到 50 条，交叉编码器的推理量直接减半。工程上的常规做法是向量召回取较大候选集，重排后只保留前 5 至 10 条交给生成模型，中间环节的取舍比换模型更影响总延迟。

这里还有一处容易踩的坑：重排分数只在一个请求内可比。阿里云百炼的文档已经明确说明了这一点，开源自建同样如此——交叉编码器输出的 logits 经归一化后的绝对值受候选集构成影响。如果实现里把重排分数写入数据库当作相关性标签复用，后续查询会出现难以解释的波动。正确做法是只用分数在本次请求内排序，把阈值判断改成「取前 N 条」或「取分数高于本次最高分一定比例的条目」。

上下文的标注方式也有两处需要小心。GLM-4.6 与 Step-3.5-Flash 的上下文是「模型卡声明值；config 实测值」并列，两者相差很小（200K 对 202,752；256K 对 262,144），可以按模型卡值理解。但 Qwen3.5 系列的「262,144 原生，可扩展至 1,010,000」需要区分：原生值来自模型配置，扩展值依赖 YaRN 之类的长度外推手段，外推后的注意力质量需要自行验证，不能按原生窗口的效果预期使用。Qwen3-235B-A22B 的「32,768 原生，YaRN 至 131,072」属于同一情况，且其原生窗口只有 32,768，在上表中属于偏小的一档，做整本文档问答时长度会成为限制。

7.4 选型建议 ​

以下建议均为基于本章素材的推断，不是实测结论。凡涉及「效果更好」的判断，都需在自有语料上评测后再定。

纯中文、成本敏感、单机私有化。 BAAI/bge-m3 是最稳的默认：1024 维、8192 长度、MIT 许可，长度足以容纳整段产品说明或法务条款。若机器只有 CPU 或小显存，退到 bge-small-zh-v1.5（512 维）或 bge-base-zh-v1.5。生成侧取 Qwen3.5-9B（稠密，9,653,104,368 参数，262,144 原生上下文，apache-2.0），是这张表里私有化门槛最低的一档。

多语言、跨语种检索。 用 Qwen/Qwen3-Embedding-0.6B/4B/8B，按显存三选一，均 apache-2.0。注意可变维度是按 MRL 截断，例如把 4096 维降到 1024 维会损失精度，需自行评测，不要默认截断后等价。

长文档、需要可变维度省存储。 Qwen3-Embedding-4B（2560 维）或 Qwen3-Embedding-0.6B（1024 维）降本；也可考虑 Conan-embedding-v2（3584 维、32K 上下文、apache-2.0），但其仓库无 config.json，工程接入需自行适配，属于有额外集成成本的选择。

多模态（检索图片或视频）。 开源选 Qwen3-VL-Embedding-8B 搭配 Qwen3-VL-Reranker-8B（均 apache-2.0，30+ 语言）；API 侧可选火山方舟 doubao-embedding-vision 系列（默认 2048 维，支持稀疏与多向量），或阿里云 qwen3-vl-rerank（33 种语言）。注意方舟侧单价与最大输入长度均未核实，做预算前必须先询价。

效果优先、能上 GPU。 Qwen/Qwen3-Embedding-8B（4096 维）与 Qwen/Qwen3-Reranker-4B 组合，两者均 apache-2.0，商用路径清晰。重排若只做中文，可在 bge-reranker-large（560M）与 bge-reranker-v2-m3 之间实测比较；多语言场景直接选 bge-reranker-v2-m3（567M，apache-2.0），是性价比与显存占用的折中点。

成本敏感、走 API。 Embedding 用阿里云百炼 qwen3.7-text-embedding-flash（0.000125 元/千 token）或 text-embedding-v4（0.0005 元/千 token）；生成用 DeepSeek deepseek-flash，空闲时段缓存未命中的输入价为 1 元/百万 token，是本章素材中的价格低位。若调用时段集中在工作日 9:00–12:00 与 14:00–18:00，实际按高峰价计，成本约为空闲价的两倍，容量规划时要按高峰价做预算。

长上下文 RAG（整本文档、长订单历史）。 生成侧可选 DeepSeek-V4.1-Flash（1M）、Kimi-K3（1M）、MiniMax-M3（1M）、Step-5-Preview（1M）、Qwen3.5 系列（262K 原生，可扩展 1M）。但需注意：超长上下文会显著抬高推理成本，优先用「检索 + 中等上下文」而不是直接把 1M 塞满。在多数企业文档问答场景中，先把检索质量做扎实比放宽上下文窗口更划算。

关于 MTEB 与 C-MTEB 榜单：素材未取得可引用的排名数值（页面为脚本动态渲染），因此本章不引用任何榜单分数。若选型需要榜单支撑，请自行重新抓取并复核原文。

榜单与直觉都不能替代自有语料评测，这也是本章所有建议都标注为推断的原因。一个可执行的最小评测流程是：从实际业务语料中抽取若干条 query，为每条标注正确的文档块，固定切块策略与候选数后，只替换 Embedding 模型或 Reranker 模型，比较召回率与首位命中率。这样得到的是相对排序，与官方文档提示的「不同配置下的绝对分数不可直接比较」的口径一致。评测时至少要覆盖两类查询：一类是关键词明确的查询，一类是需要语义匹配的查询。前者容易在小模型上得到好成绩，后者才能体现大模型与长上下文的价值。若两类查询的表现差距很大，说明问题出在切块或重排环节，而不是 Embedding 模型本身，此时换更大的模型并不能解决。

另外建议在评测阶段就固定向量库的维度上限。可变维度模型虽然灵活，但一旦上线后再改维度，需要全量重新编码与重建索引，成本远高于在评测阶段多跑几组对比。以本表的 Qwen3-Embedding-8B 为例，4096 维与截断到 1024 维是两个不同的索引方案，应在评测时同时测出质量差异，再决定是否用质量换存储。

7.5 许可与合规风险提示 ​

这一节的内容优先级高于效果对比。许可判断错误会导致产品无法商用，属于不可用返工，选型阶段必须逐条落定，不能默认「开源即可商用」。

明确禁止商用。 TencentBAC/Conan-embedding-v1 的 HF 许可为 CC-BY-NC-4.0，即禁止商用。该模型规格（325,522,432 参数、1024 维、512 长度、中文）在中文短文本检索场景中有吸引力，但任何面向商业交付的系统都不得将其纳入。若需要同族能力，改用 Conan-embedding-v2（apache-2.0，3584 维、32K 上下文），代价是需要自行适配无 config.json 的仓库结构。

许可标签为 other，商用前须逐条核对官方许可文本。 涉及 GLM-5.3、Kimi-K3、MiniMax-M3、Step-5-Preview 等模型，另有 Kimi-K2.5、Kimi-K2-Thinking、MiniMax-M2.5。other 只表示 HuggingFace 未映射到标准许可标识，不等于无限制开源，也不等于禁止商用——它表示必须读原文才能判断。其中 Step-5-Preview 的模型卡已给出具体名称：StepFun Model License 1.0（标签仍为 other），应直接以该许可全文为准。本章未取得任何一个 other 标签对应的条款内容，因此不对其商用可行性做任何判断。

非标准开源许可。 bge-multilingual-gemma2 与 bge-reranker-v2.5-gemma2-lightweight 为 Gemma 许可，不是标准开源许可。Gemma 许可通常包含使用限制与分发义务，与 MIT、apache-2.0 不可等同处理，纳入前应单独走一遍法务确认。

同族替换是较清晰的合规路径。 在需求允许的前提下，优先选择同族的宽松许可版本：GLM-5.2、GLM-4.6 为 MIT，Step-3.5-Flash 为 apache-2.0。它们与 other 标签的同族模型能力定位接近，但许可边界明确，能显著降低合规评审成本。

存量下线的服务。 阿里云百炼 gte-rerank-v2 的官方公告下线日期为 2026-05-30，应改用 qwen3-rerank。需要注意两点：其一，本章来源标注的抓取与查看日期为 2026-11-24，该日期已晚于下线日期，若仍在使用该服务，应立即核实账号下的实际可用状态，不要依赖本文档的结论；其二，素材中该条目的原始表述为「将于 2026-05-30 下线」，属公告时点的未来时态，与本文档的查看日期存在时态差异，按本文档口径应表述为「已于 2026-05-30 下线」。此外，gte-rerank-v2 与 qwen3-vl-rerank 都不支持 OpenAI 兼容接口，迁移时不能只改模型名，调用客户端也要一并调整。

其他需要在合规评审中一并确认的点。 core-emb-*、core-reranker-*、UEmbed-9B 为 CC-BY-4.0，属于非标准开源许可，通常带署名要求，需确认分发场景下的署名方式。moka-ai/m3e-large 未标注许可，moka-ai/m3e-base 的许可与参数量均未核实，shibing624/text2vec-large-chinese 仓库返回 HTTP 401、全部字段未核实——这三者的许可状态都属于无法确认，不应在有合规要求的项目中使用。火山引擎方舟 doubao-embedding-vision-250615 已停止新购、存量可用，新项目不应再以它作为方案基线。最后，来源中标注为 license:other 的模型，其具体条款内容在本次抓取中均未取得，任何商用决策都必须以官方许可全文为准，不能以本章表格作为依据。

把上述风险收成一张决策清单，选型评审时按顺序过一遍即可。第一步，看许可标识：MIT 与 apache-2.0 可以直接推进；CC-BY-NC 直接排除；CC-BY-4.0 确认署名义务；Gemma 许可与 other 标签一律停下，读原文后再判定。第二步，看证据完整性：规格中只要有关键字段是「未核实」，就要判断该字段是否影响部署决策。参数量未核实不影响功能，但影响显存预算；许可未核实则直接阻断商用。第三步，看服务在架状态：云服务要确认是否已公告下线、是否已停止新购。第四步，看同族是否有宽松许可的替代版本，有则优先替换，用能力上的小幅让步换取合规路径的确定性。

需要强调本章的能力边界：这里只对许可状态做归类与提示，不做法律判断。CC-BY-NC-4.0 禁止商用这一条结论直接来自许可标识本身，属于可确认的事实；而 other 标签下各模型究竟允许什么，本章既未取得条款文本，也不具备解释条款的依据，必须由法务或厂商官方答复来定。把「未核实」当作「默认可商用」是最危险的误读，本章特意保留这些空白单元格，正是为了避免这种误读。
